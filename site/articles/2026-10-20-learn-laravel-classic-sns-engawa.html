この講座では、日記、マイミク、コミュニティ、足あとを中心にした会員制SNS「えんがわ」を作ります。2026年10月20日に確認したLaravel 13系と公式React Starter Kitを基準に、macOSでの開発環境、実装、メールと画像の取り扱い、Laravel Cloudへのデプロイ、公開後の運用まで進みます。

対象は、JavaScriptやReactには触ったことがあり、Laravelで一つのサービスを完成させたい人です。PHPの構文は第3章で補います。Laravelの経験は前提にしません。macOSを主手順にし、WindowsではWSL2内にPHP・Composer・Nodeをまとめ、Dockerへ接続すれば、プロジェクト作成以降の同じ手順を使えます。

なぜReactとInertiaを選ぶのか

この節のリンク章内の目次へ

LaravelをJSON APIサーバーにして、別のSPAからfetchする構成も作れます。この講座では、一つのアプリにルート・認証・画面をまとめます。Reactの知識を使いながら、Laravelの通常のControllerとsession認証を学べるためです。

最初のページ表示はLaravelからHTMLを返し、その後のページ移動やフォーム送信はInertiaが調整します。Controllerは画面名とpropsを返します。フロントから自由に呼べる公開APIを別途設計したことにはならず、モバイル向けAPIが必要になった段階でAPI Resourcesやトークン認証を追加します。Inertiaの仕組み

SNSの中心処理はPHPに置きます。Reactは「何を見せるか」「どんな入力を送るか」を担当し、誰が日記を読めるかは決定しません。ブラウザに送られたpropsは利用者が読むことができるため、表示を消すだけでは非公開になりません。

PHPの構文を最小限覚える

$user が変数、-> はインスタンスのプロパティやメソッドへのアクセス、:: はクラス名を使う呼び出しです。User $user と : string は実行時にも意味のある型宣言です。namespace はクラスの名前空間、use は短い名前で参照する宣言です。

ここで投稿者を $request->input('user_id') から取得しません。ブラウザの値は変更できるので、認証済みユーザーから決めます。

ユーザーIDが4と9なら、申請の向きにかかわらず user_low_id=4, user_high_id=9 にします。申請した人は requested_by に残します。

UNIQUE(user_low_id, user_high_id) によって、4→9と9→4の二重登録を防ぎます。CHECK(user_low_id < user_high_id) は並び方と自己申請禁止をDB側でも守ります。

それでも exists() のあとに create() するだけでは、同時リクエストがどちらも未存在と判断できます。第8章では、必ず存在するusersの2行を同じ順番でロックしてから関係を変更します。まだ存在しないfriendshipの行へ lockForUpdate() しても、それだけでは同じ効果になりません。

cascadeがしてくれることと、してくれないこと

この節のリンク章内の目次へ

日記を消すとコメントやmediaのDB行も消す設計にできます。これはSQLの参照整合性です。S3上のファイルはSQLの外にあるので、自動では消えません。また、DBのcascadeで消える各行についてEloquentの削除イベントが必ず個別発火する、とは扱いません。

そのため、物理画像の削除はMediaStorageを通して処理し、外部ストレージの削除Jobをtransactionのcommit後に送ります。退会やコミュニティ削除も、cascade前に必要な削除対象を確保する必要があります。

何にindexを付けるか

この節のリンク章内の目次へ

日記の一覧は投稿者と作成時刻をよく使うため、user_id, created_at が候補になります。マイミクはペアのuniqueに加えて、どちら側のユーザーからも検索できるindexが必要です。足あとは持ち主と最終訪問時刻から検索します。

indexは全列へ付けるものではありません。書き込み時の更新コストと容量も増えます。まず実際のWHEREとORDER BYに合わせ、件数が増えたらPostgresのEXPLAINで調べます。第14章の %キーワード% 検索は、通常のB-tree indexだけで速くなるとは考えません。

この節のリンク章内の目次へ

engawa が開発DB、engawa_test が自動テストDBです。PHPUnit設定からSQLiteの :memory: を削除し、PostgreSQLのテストDBへ向けます。RefreshDatabase はテーブルを作り直すことがあるため、ここを間違えると開発データを失います。

日本語の部分一致検索、CHECK制約、transactionやロックを学ぶ講座なので、最終確認は本番と同じDB系統で行います。SQLiteだけでテストが通ることをPostgresでの同時実行の証明にしません。

6 マイミクを一組一行で表す

この節のリンク章内の目次へ

会員IDが3と8なら、申請した方向にかかわらず次の組み合わせで保存します。

申請した人はrequested_byに記録します。これにより、3→8と8→3を別の友達関係として作ってしまうことを防げます。

DBの制約は次のとおりです。

制約 守ること
UNIQUE(user_low_id, user_high_id) 一組一行
CHECK(user_low_id < user_high_id) 並び順を固定し、自分自身を除外
CHECK(requested_by IN (...)) 申請者が当事者のどちらか
CHECK(status IN ('pending', 'accepted')) 想定外の状態を保存しない

申請中ならpending、受信者が承認したらacceptedです。取消、辞退、解除では行を削除します。履歴が必要になったら別の監査テーブルを追加できますが、基本講座では現在の状態だけを管理します。

同時申請への対策

二人が同時に申請すると、両方の処理が「friendshipはまだない」と判断する可能性があります。存在しないfriendshipを lockForUpdate() で検索しても、その行はロックできません。

そこで必ず存在している二人のusers行を、IDの昇順でロックします。

先にロックを取った処理が終わるまで、もう一方は待ちます。待ち終わった処理はfriendshipの現在値を読み直すので、重複作成を避けられます。末尾の3は、トランザクションがデッドロック等で再試行可能な場合の試行回数です。

並び順を統一することも大切です。一方が会員3→8、他方が8→3の順にロックすると、互いの解放を待つ状況が生まれやすくなります。申請、承認、解除、ブロック、ブロック解除をすべてSocialGraphへ集め、同じロック規約を使います。

反対向きの申請で勝手に承認しない

受信した申請が存在する状態で「申請」APIを呼んでも、参照実装は自動承認しません。既存のpending行を返し、明示的な「承認」操作を求めます。

承認APIは、ログイン会員が当事者であり、かつ申請者ではないことを確認します。URLのfriendship IDを変更しても、第三者は承認できません。同じ承認を再送した場合は、通知をもう一度発行しません。

7 ブロックは一方向に保存し双方に適用する

この節のリンク章内の目次へ

blocksの1行は、「AがBをブロックした」という方向を持ちます。設定画面で解除できるのは自分が作った行だけです。

一方、日記の閲覧判定では「AがBをブロック」「BがAをブロック」の両方を調べます。どちらかが存在すれば相互の表示を拒否します。

9 足あとを実際の閲覧で記録する

HTTP 役割

11 三人で公開範囲を検証する

この節のリンク章内の目次へ

シードまたは通常登録で、Alice、Bob、Carolの三会員を用意します。ブラウザプロファイルやプライベートウィンドウを使い、ログイン状態が混ざらないようにします。

  1. Aliceがmembers、friends、privateの日記を一つずつ作る。
  2. BobとCarolは、最初はmembersだけ読めることを確認する。
  3. AliceからBobへ申請する。未承認のBobがfriends日記を読めないことを確認する。
  4. Bobが承認し、Bobだけがfriends日記を読めることを確認する。
  5. Carolが日記URLや画像URLを直接入力しても拒否されることを確認する。
  6. Bobでfriends日記の画像URLを控え、マイミク解除後に再アクセスする。次のリクエストが拒否されることを確認する。
  7. AliceがBobをブロックし、検索、プロフィール、コメント、足あと、通知でも相手の内容が表示されないことを確認する。
  8. ブロックを解除し、マイミクが自動復活しないことを確認する。

この節のリンク章内の目次へ

1日1件をDBで守る

この節のリンク章内の目次へ

owner_id は訪問された人、visitor_id はログインユーザーです。フォームからvisitorを受け取りません。UNIQUE(owner_id, visitor_id, visited_on) によって、同じ人の同日訪問は1行へまとまります。

自己訪問と、ブロック関係のある相手への訪問は記録しません。直接POSTされた場合も、プロフィールが閲覧可能かを確認します。

通常のFeature testで「申請→もう一度申請」を行うだけでは、二つの接続が同時に書き込む競合を実証しません。本教材はcanonical pairのunique制約と、既存users行を順にロックする設計を採用していますが、競合の本格試験は次の手順で追加できます。

  1. 独立したPostgres接続を二つ用意する。
  2. 同じ二人についてA→BとB→Aの申請を同時開始する。
  3. 片側がロックを保持している間、もう片側が待機することを確認する。
  4. commit後、friendshipが一行だけでpendingのままであることを確認する。
  5. ブロックと承認、画像3枚目と4枚目でも同様に行う。

順番をそろえたロックでも、複数の機能を組み合わせるとdeadlockは起こり得ます。外部ストレージへの書き込みを含むtransactionを、無条件に再実行して同じ副作用を増やさないようにします。

17.7 Cloud Managed Queueを作る

この節のリンク章内の目次へ

ローカルではQUEUE_CONNECTION=databaseを使い、別ターミナルでworkerを動かしました。本番ではEnvironmentへManaged Queueを追加します。

  1. Environmentの構成画面でAdd compute → Managed queueを開きます。
  2. Standard queueとFlex computeを選びます。
  3. 名前を例としてsocialにし、最初はキュー1個、workerの上限1程度で始めます。
  4. 最初に作ったキューがdefaultになります。既存キューがある場合は、このキューのメニューからSet as defaultを選びます。
  5. 保存してデプロイします。

Managed QueueはWebとは独立して起動します。Webをscale-to-zeroにしても通知Jobを処理できます。逆に、App cluster上で自己管理のqueue:workを動かして一緒にsleepさせる構成では同じ保証になりません。本講座ではManaged Queueだけを使い、同じJob用のworkerを重複追加しません。Managed Queues / Compute

このSNSでqueueに入るのは、NotifySocialActivityとDeleteMediaObjectです。前者はDB更新のcommit後に開始し、相手との関係・ブロック・日記の閲覧権限を再確認します。内部のSocialActivity通知は同期で送るため、通知を二重にqueueへ投入しません。

一方、スターターキット標準のメール認証とパスワード再設定はこのJobを経由しません。これらが届いていても、SNS通知のqueueが動いている証明にはならない点を覚えておきましょう。

18.3 Queueの失敗を直す

この節のリンク章内の目次へ

ローカルのdatabase queue

workerが動いていることを確認します。

失敗Jobを確認し、原因を修正してから対象IDだけを再実行します。

引用符の中をqueue:failedで表示された実際のIDへ置き換えてください。queue:retry allを何度も実行する運用から始めず、1件で改善を確かめます。--timeoutはconnectionのretry_afterより十分短く設定します。例えば60秒と90秒の組み合わせです。これは同じJobが重なって処理される危険を減らす設定です。Laravel Queues

本番のCloud Managed Queue

Cloud Monitoring → Queuesを開きます。失敗したJobの例外を読み、環境変数・コード・外部サービスの状態を修正してデプロイしてから、そのJobをRetryします。

Managed Queuesではqueue:failed、queue:retry、queue:clearやHorizonを運用画面として使いません。CloudのQueues画面またはCloud APIを使います。Web側のscale-to-zeroとManaged Queueは別のcomputeなので、Webが休止していることだけを原因と判断しないでください。Managed Queues

再試行と重複を理解する

本教材のNotifySocialActivityは、Job作成時に通知UUIDを1つ決め、再試行にも同じUUIDを使います。同じJobが再実行されたとき、database通知が存在すればその再作成を省きます。WithoutOverlappingも使い、同じJobを同時処理することを避けています。

ただし、外部メールサービスが送信を受け付けた直後に通信が切れると、アプリは成功したか判断できない場合があります。この場合の再試行ではメールが重複する可能性が残ります。本教材はメールに日記本文・タイトル・投稿者名を入れず、一般的な案内と通知画面へのリンクだけを送ります。厳密な一回送信が必要になったら、送信記録とproviderのidempotency keyを組み合わせたoutboxを追加する課題に進みます。

通知Jobは送信前に現在の権限を再確認します。申請が取り消された、友人が解除された、相手が退会した、blockされた場合は通知されないことがあります。これは配送障害とは限りません。

18.4 メールの問題を切り分ける

この節のリンク章内の目次へ

次の4段階を分けて考えます。

  1. アプリがメール送信処理を呼んだか。
  2. Resendがリクエストを受け付けたか。
  3. 受信側のメールサーバーが受け付けたか。
  4. 受信者の受信箱に表示されたか。

APIで成功したことと、受信箱に入ったことは同じではありません。Resendの送信履歴、失敗理由、迷惑メールフォルダを確認します。FromのdomainがVerifiedか、APP_URLが正しいかも確認します。

標準のメール認証・reset mailと、SNS通知mailは経路が異なります。認証mailだけ届く場合はQueueを確認します。SNS通知欄に表示されてもmailが届かない場合は、プロフィールのメール通知設定とResend側を確認します。

利用者が増えたら、bounce・complaintを記録するWebhookと、継続的に配送できないアドレスへの送信停止を追加します。Webhookは署名を検証し、同じeventが再送されても二重処理しないようevent IDを保存します。必要性が出る前に高度な仕組みを増やすより、最初は送信履歴の確認を確実に行います。Resend Webhooks

18.5 画像の整合性を保つ

この節のリンク章内の目次へ

DBとObject Storageは別々に失敗する

画像には2種類のデータがあります。DBのmedia行は所有者・日記との関係・保存先を表し、Object Storageには実際の画像のbytesがあります。

本教材は次の順序にしています。

操作 順序 失敗時
追加 画像を正規化→object保存→media行作成 DB作成失敗ならobjectをcleanup
差し替え 新画像を保存→DB更新をcommit→旧画像削除Job 旧画像の削除だけ再試行可能
削除 media行を削除→commit→object削除Job 画面上は即座に消え、物理削除は再試行

日記削除では、DBのcascadeだけに任せず、先に対象MediaをMediaStorage::delete()へ渡します。退会でも同じ処理が必要です。ストレージ内に一時的に残っていてもprivate bucketなので、公開URLから誰でも読める構成にはなっていません。

プロセスがobject保存直後に強制終了した場合など、例外処理だけで回収できない孤立ファイルは残り得ます。定期的な整合性確認を発展課題として追加します。

  1. 24時間以上前に作られたobjectだけを対象にする。
  2. 対応するdisk/pathを持つmedia行がないものを候補にする。
  3. 最初は候補数とサイズを報告するdry-runにする。
  4. 誤判定がないことを確認してから削除モードを有効化する。

新しいuploadを処理中のobjectまで即座に消す実装にしないでください。WebとQueue workerのローカルディスクは共有されないため、非同期画像処理へ変更する場合も、まず共有Object Storageへ保存してからそのpathをJobへ渡します。Cloudのworker filesystem

画像変換の確認

MediaStorageはLaravel Image APIでEXIFの向きを補正して縮小し、可逆PNGを経由します。その後、新規GD canvasへ画素だけを転写してWebPへ変換します。元のEXIF/GPS/XMPなどをそのまま転送しないための処理です。Laravel Image / PHP GD

正立した写真、縦向きEXIF付き写真、透明PNG、JPEG拡張子へ改名した不正ファイルを試します。保存された画像の形式とサイズを調べ、位置情報が残っていないことも確認します。人物や住所が写真自体へ写っている場合は、metadata除去で消えるわけではありません。

18.6 権限の回帰を確認する

この節のリンク章内の目次へ

日記ページでボタンを隠すだけでは、URLを直接呼ばれたときの保護になりません。新しい機能を追加したときは、以下を同じアクセス規則で守ります。

  • タイムラインと検索結果。
  • 日記詳細とコメント一覧。
  • 日記の画像route。
  • 通知一覧から開くリンク。
  • コミュニティとトピック。

本教材の通知一覧は最新500件を候補として取得し、現在読めない通知を除いてから20件ずつページ分割します。全履歴の保管庫ではありません。件数が増えたら履歴画面や検索用のprojectionを設計してください。

一度見えた友人限定画像が、友人解除・公開範囲変更後の再リクエストで見えなくなることを確認します。すでに受信者が保存したbytesを取り消すことまではできません。ここで確認するのは、サーバーが今後の取得を拒否することです。

18.7 バックアップと復元を一度試す

この節のリンク章内の目次へ

バックアップの設定値を見るだけでは、復元できるかは分かりません。練習段階で別DBへの復元を一度行います。

DB

Cloud PostgresでPITRの保持を有効にします。復元対象時刻を選び、新しい名前のDBとして復元します。Cloudのrestore APIも、既存DBへ直接上書きするのではなく、新しいDBを返す構造です。Postgres / Restore API

復元したDBは本番とは別の検証環境へ接続します。メールは外部に送らない設定にし、以下を確認します。

  1. users、diaries、friendships、mediaの件数が妥当。
  2. テストアカウントでログインできる。
  3. 日記の公開範囲とblockが復元されている。
  4. mediaのpathに対応する画像が存在する。
  5. 必要なmigrationがどこまで適用されているか確認できる。

画像

DBのバックアップには画像のbytesは含まれません。Object Storageについても別bucketへのコピーや定期export、保持日数を設計します。単なる同期では、元の誤削除がコピー先へ反映されてしまう場合があるため、世代を残すか削除猶予を付けます。

DBを3日前へ戻しても、昨日すでに物理削除した画像が戻るとは限りません。DBの保持期間と画像の保持期間を対応させることが重要です。

目標を言葉にする

学習用の例として「最大1日分の投稿損失まで許容し、半日以内に検証環境で復旧を確認する」のように目標を決めます。これは本教材の保証値ではなく、自分で選ぶ運用目標です。必要な保持期間・手順・費用をこの目標に合わせます。

18.8 DB変更は二段階以上に分ける

この節のリンク章内の目次へ

コードのrollbackとDBのrollbackを同じ操作と考えないようにします。例えばbody列をcontentへ変更する場合、いきなりrenameすると旧コードが動かなくなります。

  1. contentをnullableで追加する。
  2. 新旧両方を扱えるコードを公開する。
  3. 既存データを小さなbatchで移す。
  4. 新列へ切り替え、動作と件数を確認する。
  5. 旧コードへ戻す必要がなくなってから旧列を削除する。

この方法なら、Webの旧プロセス、実行中のJob、新コードが一時的に混在しても対応しやすくなります。migrate --forceが成功するだけで、旧コードとの互換性まで保証されるわけではありません。

大量のbackfillをdeploy commandに詰め込まず、進捗を残せるcommandやJobへ分けます。本番のmigrationを安易にrollbackしてデータを消すより、追加のmigrationで修正できるか先に考えます。

足あとのPOST

この節のリンク章内の目次へ

members/show.tsxは画面mount後のeffectでPOST /members/{id}/footprintを行います。React StrictModeによる二重effectはrefで抑止し、backendは同一人・同一日のunique制約でも重複を防ぎます。

このPOSTはInertiaのrouterを使います。Controllerはback(303)を返してください。204を返すとInertiaの正規レスポンスでないため、エラーモーダルの原因になります。GETやリンクのprefetchだけでは記録しません。

他人のプロフィールには、訪問によって足あとが記録され、30日間保持される旨を表示しています。保持期限の処理は第12章と第18章で扱います。

フォーム

この節のリンク章内の目次へ

SNSのフォームはuseFormによるredirect-based validationを使用します。FormErrorsとfield単位のerrorを表示し、送信中のbuttonを無効化します。退会フォームはStarter KitのFormを維持しています。日記や画像の削除、退会、ブロックなどの操作には確認dialogがあります。

日記はテキストを先に保存し、詳細画面の別フォームで1枚ずつ画像を追加します。画像フォームはFormDataで送信し、fieldはimageまたはavatarです。日記ごと3枚の上限は、UIとbackend双方で確認します。

日記・コメント・自己紹介・コミュニティ紹介文はReactの通常text nodeで描画します。改行はwhitespace-pre-wrapで表示し、生HTMLを挿入しません。

検証

この節のリンク章内の目次へ

WayfinderはStarter Kitのルート関数とフォーム用の型を生成します。初回に型検査だけを実行すると@/routesや.form()が見つからないことがあるため、--with-form付きの生成を先に行います。現在のVite設定ではビルド時にも生成します。

現行kitはVite+のpnpm run checkでformatとlintを検査します。自動整形にはpnpm run check:fixを使います。このチェックはkit自体のformatやlintの規約も対象になるため、検出された内容を読んで調整してください。PHP側はvendor/bin/pintで整形します。

ブラウザでは、幅が狭い画面、キーボード操作、入力エラー、二重送信防止、画像upload後の更新、空の一覧と複数ページ、別ユーザーへの日記・画像アクセスを確認します。
