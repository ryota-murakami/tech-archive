1背景 — なぜ「確定」という概念が要るのか

英語のテキスト入力は、驚くほど素直です。k キーを押せば k が入る。キーを押した回数と、画面に増える文字の数が一致している。ブラウザのイベントモデルも、その素直さを前提に設計されました。キーを押す（keydown）、文字が入る（input）、キーを離す（keyup）。それだけです。

ところが日本語では、この一致が崩れます。「図面」と入力したいとき、私たちはまず z u m e n と 5 回打ち、変換キーを押し、候補の中から「図面」を選び、Enter で確定します。打鍵は 5 回以上あるのに、最終的に入るのは 2 文字。しかも打っている途中の画面には ずめん という、まだ本物ではない文字列が表示されている。

この「まだ本物ではない文字列」を作っているのは、ブラウザでもキーボードでもなく、OS の入力メソッド（IME: Input Method Editor）です。IME はキーボードとアプリケーションの間に立ち、打鍵を溜め込み、変換し、ユーザーが納得したタイミングで初めてアプリに文字を引き渡します。

入力欄の中で起きていること — 点線の下線が付いている部分が「まだ IME が握っている、確定前の文字」です

変換中（未確定）
ずめーん
確定後
ズメーン
用語

composition（コンポジション / 変換セッション）とは、IME が「今この人は文字を組み立てている最中だ」と認識している一区切りのことです。始まりがあり、途中経過があり、終わりがあります。この一区切りを Web アプリ側から観測するための仕組みが、Composition Events です。

なぜアプリ側がこれを知る必要があるのでしょうか。理由は 2 つあり、どちらも実害を伴います。

ひとつは Enter キーの意味が変わること。変換中の Enter は「この候補で確定する」という意味ですが、変換していないときの Enter は「フォームを送信する」「次のセルへ移動する」という意味になります。区別しないと、変換を確定しようとした瞬間にフォームが飛んでいきます。

もうひとつは 途中経過の文字列が「正しくない」こと。ローマ字入力の途中には ｚ や ずｍ といった、日本語としては存在しない文字列が現れます。1 打鍵ごとに検証を走らせる作りだと、この途中の文字列に対してエラーが出たり消えたりを繰り返します。

2背景（近景） — 3 つの composition イベント

ブラウザは、この変換セッションを 3 つのイベントで通知します。W3C UI Events 仕様は、この 3 つの相互の順序だけを規定しています。

仕様の原文

“The Composition Events defined in this specification MUST occur in the following set order relative to one another: 1. compositionstart 2. compositionupdate (Multiple events) 3. compositionend”

出典: W3C UI Events §3.6.2 Composition Event Order

イベントいつ飛ぶかdata の中身BubblesCancelable
compositionstart変換セッションが始まったとき空文字（実測）YesYes
compositionupdate未確定文字列が変わるたび（複数回）その時点の未確定文字列YesNo
compositionend変換が確定またはキャンセルされたとき最終的に確定した文字列YesNo

Bubbles / Cancelable は W3C UI Events のイベント型テーブルより。data の説明は同仕様「the characters generated by an input method」および MDN より。

ここで compositionend の定義に、見落としやすい言葉が入っています。MDN の表現を借りると、このイベントは変換セッションが “completes or cancels” したときに発火します。つまり Esc で変換を取り消したときにも飛んでくる。「compositionend が来た＝ユーザーが文字を確定した」と読むのは、半分しか正しくありません。

よくある誤解

compositionend は「確定イベント」ではなく「変換セッションの終了イベント」です。確定でも終わるし、取り消しでも終わる。取り消しの場合、event.data は空文字になります（＝入力欄には何も残らない）。data の中身を無条件に信用して処理を分岐させると、Esc を押したユーザーの入力欄が壊れます。

3直感 — 「下書き」と「清書」

仕組みを一言で言えば、こうなります。

核心

変換中、入力欄には IME の下書きが仮置きされている。compositionend は、その下書きが消えて清書が確定した瞬間を知らせるイベントである。

「下書きも入力欄の value に入っている」というのが、この話の面白いところです。input.value を読むと、変換中でも "ずめーん" が返ってきます。ブラウザは下書きと清書を value の上では区別しません。区別できるのは、イベントの側だけなのです。

idle

value = 清書だけ
最初の打鍵
⟶
compositionstart
composing
変換中
value = 清書 + 下書き
composing
変換中
Enter で確定 / Esc で取消
⟶
compositionend

value = 清書だけ
（取消なら元のまま）

そして composing の状態にいる間も、打鍵のたびに input イベントは飛んできます。これが最大の落とし穴です。「onChange を見ていれば入力は全部拾える」というのは正しいのですが、拾えてしまうものの中に下書きが混ざっている。React の公式ドキュメントも onChange を「Behaves like the browser input event」と説明しています。出典: React 公式ドキュメント react-dom/components/input.md（Context7 経由）

「ずめーん」と打って「ズメーン」に変換するまでに、input イベントは 6 回飛ぶ — その 6 回はすべて下書きです

input #1
ｚ
input #2
ず
input #3
ずｍ
input #4
ずめ
input #5
ずめー
input #6
ずめーん

「ｚ は全角カタカナではありません」というエラーを、この 6 回のうち 3 回出してしまう。これが冒頭に書いた「エラーが点滅する」の正体です。compositionend は、この騒がしさを黙らせるためのスイッチとして使われます。

4仕組み — 実測したイベントの並び

ここからは推測をやめて、実際に測ります。素の <input> を持つページを用意し、Chrome DevTools Protocol の Input.imeSetComposition で本物の変換セッションを発生させ、飛んできたイベントを全部記録しました。

// 計測ハーネス: すべてのイベントを value ごと記録する
const types = ['keydown','keyup','compositionstart','compositionupdate',
               'compositionend','beforeinput','input','change']
for (const type of types) {
  el.addEventListener(type, (e) => window.__log.push({
    type: e.type, data: e.data, isComposing: e.isComposing, value: el.value
  }))
}

// 駆動: ローマ字を1文字ずつ積んでいき、最後に確定する
for (const text of ['ｚ','ず','ずｍ','ずめ','ずめー','ずめーん']) {
  await cdp.send('Input.imeSetComposition',
    { text, selectionStart: text.length, selectionEnd: text.length })
}
await cdp.send('Input.insertText', { text: 'ズメーン' })  // 変換して確定

この生ログから、実務に効く事実が 3 つ読み取れます。

事実 1 — compositionend は最後に来る（Chrome では）

行 22 と 23 に注目してください。確定時の input は compositionend の前に来ており、しかもその isComposing は true です。そして compositionend の後には、isComposing: false の input が来ません。

ここが罠

「onChange の中で isComposing が false のときだけ処理する」という書き方は、Chrome では IME 入力に対して一度も発火しません。変換中の input はすべて isComposing: true、確定時の input も true、そして確定後に input は来ないからです。
変換確定のタイミングで値を書き換えたいなら、compositionend を直接聞く以外にありません。

逆に言えば、compositionend が最後に来るということは、そこで value を書き換えても後から上書きされないということでもあります。安心して正規化処理を置ける場所なのです。

事実 2 — compositionupdate の時点では value はまだ古い

行 5 をもう一度見てください。compositionupdate の data は "ず" なのに、el.value はまだ "ｚ" のままです。値が実際に DOM へ反映されるのは、その次の input イベントのタイミング。

実装上の帰結

compositionupdate のハンドラで e.currentTarget.value を読むと、1 ステップ古い値が取れます。最新の未確定文字列が欲しければ e.data を読んでください。
（compositionend では両者が一致するので、この問題は起きません — 行 23 で data と value はどちらも "ズメーン"）

事実 3 — keydown にも isComposing が付く

Enter キーの問題を確かめるため、2 本目の計測をしました。変換中に Enter を押し、確定させ、もう一度 Enter を押しています。

Chrome 152。Input.dispatchKeyEvent で Enter を 2 回、変換の前後に分けて送っています。

2compositionupdatedata="ずめ"

4inputisComposing=true   value="ずめ"

6keyupkey=Enter   isComposing=true
7compositionupdatedata="ズメ"   value="ずめ"

行 5 と行 11 は、どちらも「Enter の keydown」です。人間にとっては全く違う操作なのに、e.key だけを見ると区別が付きません。区別できる唯一の手がかりが isComposing であり、実測どおり 行 5 は true、行 11 は false になっています。

// これだけで「変換確定の Enter」と「送信の Enter」を分けられる
const handleKeyDown = (e) => {
  if (e.nativeEvent.isComposing) return   // 変換中の Enter は IME のもの。触らない
  if (e.key === 'Enter') submit()
}
仕様の定義

isComposing は “true if the input event occurs as part of a composition session, i.e., after a compositionstart event and before the corresponding compositionend event.” と定義されています。「compositionstart の後、対応する compositionend の前」という、まさに区間の内側を表すフラグです。

出典: W3C UI Events（InputEvent の isComposing 定義）

どこに isComposing があるか

isComposing を持っているのは InputEvent（= input / beforeinput）と KeyboardEvent（= keydown / keyup）だけです。CompositionEvent には無い — 実測でも composition 系の行はすべて undefined でした。onCompositionEnd のハンドラで e.isComposing を読んでも undefined しか返りません。

仕様が決めていないこと — input と compositionend の順序

ここまで「Chrome では」と繰り返してきたのには理由があります。仕様が保証しているのは composition 3 兄弟の相互の順序だけで、input がその中のどこに挟まるかは規定されていないのです。そして実際、エンジンごとに違います。

エンジン確定時の順序確定時の input の isComposing出所
Blink（Chrome / Edge） input → compositionend true（後続 input なし） 本日実測
WebKit（Safari） input → compositionend true w3c/uievents #202
Gecko（Firefox・従来） compositionend → input false w3c/uievents #202 / Bugzilla 1305387
Gecko（2025-01 の Intent to Ship） input(true) → compositionend → input(false) 両方飛ぶ mozilla dev-platform

出典: w3c/uievents #202 “Event order between compositionend and input”（2018-04-21、現在も Open） ／ Bugzilla 1305387 ／ Intent to ship: Dispatch input event before compositionend（2025-01-16）

Firefox の 2025 年の提案が興味深いのは、Chrome に合わせるのではなく、両方を出すという解決を選んでいる点です。Chrome 互換のために compositionend の前に冗長な input を足しつつ、従来の isComposing: false な input も残す。互換性のために重複を許容した、いかにも Web らしい決着です。

未検証

Firefox と Safari の実挙動は、この場では計測していません。 CDP の Input.imeSetComposition は Chrome 専用で、他エンジンでは変換セッションを合成できないためです。上表の Gecko / WebKit 行は仕様議論とバグトラッカーからの引用です。

特に 2025-01 の Firefox Intent to Ship がどのバージョンで出荷されたか（そもそも出荷されたか）は特定できませんでした。 Bugzilla 1305387 は今も Open のままです。確かめるには、実機の Firefox で本物の IME を使って上と同じハーネスを開き、イベント順を目で見るのが確実です。

未検証（もうひとつ）

今回の計測は CDP でイベントを合成したものであり、macOS の日本語入力そのものを駆動したわけではありません。compositionupdate → beforeinput → input という並びは、Blink の過去の告知（「beforeinput を compositionupdate の前に出す」）とは逆に見えます。Chrome 152 の実挙動としてはこの並びですが、実 IME で完全に同じ並びになるかは実機確認が要ります。

パターン A — Enter とセル移動を守るガード（多数派）

表形式の入力 UI が多いこのアプリでは、変換中の Enter / Tab が「セル移動」として解釈されてしまう事故を防ぐのが主用途です。2 つの書き方が併存しています。

A-1. e.nativeEvent.isComposing を直接読む

// src/components/forms/input/SuggestionDropdown.tsx:151
const handleKeyDown = useCallback((e) => {
  if (e.nativeEvent.isComposing) {
    if (onKeyDown) onKeyDown(e)
    return            // 候補ドロップダウンの矢印キー操作より IME を優先する
  }
  // ArrowDown / Enter などの処理…
})

ハンドラが 1 つで済み、React の state を増やさない。キーイベントだけを見たいならこれが最小です。

A-2. isComposingRef に自分で記録する

// src/features/shared/transaction_document_modal/.../TableCellTextInput.tsx:113,290,445
const isComposingRef = useRef(false)

// keydown 側
if (isComposingRef.current) {
  // IME入力中はセル移動等でフォーカスが外れないようにする
  e.stopPropagation()
}

// JSX 側
<Input
  onCompositionStart={() => (isComposingRef.current = true)}
  onCompositionEnd={() => (isComposingRef.current = false)}
/>

こちらは keydown 以外のイベント（親テーブルの監視、blur など）からも変換中かどうかを知りたいときの書き方です。useRef なので再レンダリングを起こしません。同じファイルで 4 つの Input に同じ 2 行が付いています。

使い分け

キーイベントの中だけで判定が完結するなら A-1（e.nativeEvent.isComposing）。別のイベントハンドラから参照したいなら A-2（isComposingRef）。useState にしている箇所（InputCellStringType.tsx:94）もありますが、変換中かどうかで描画が変わらないなら useRef の方が無駄な再レンダリングを避けられます。

パターン B — 確定時に値を正規化する（取引先の読み（カナ）欄）

もうひとつの用途が、今日ちょうど実装した「ひらがなを打ったら全角カタカナに直す」欄です。ここでは compositionend を値の書き換えとエラー表示の抑制の両方に使っています。

// src/views/settings/client_settings/.../ClientForm.tsx:87-131
const [isNameKanaComposing, setIsNameKanaComposing] = useState(false)

// 変換確定の瞬間に全角カタカナへ直す
const onNameKanaCompositionEnd = useCallback((event) => {
  setIsNameKanaComposing(false)
  alignNameKanaDisplay(event.currentTarget.value)
}, [alignNameKanaDisplay])

// 貼り付けなど IME を経由しない入力もあるため、blur でも直す
const onNameKanaBlur = useCallback((event) => {
  alignNameKanaDisplay(event.target.value)
}, [alignNameKanaDisplay])

// 変換中はエラーを「表示しない」だけ。検証自体は止めない
const nameKanaErrorMessage = useMemo(
  () => (isNameKanaComposing ? undefined : errors.nameKana?.message),
  [isNameKanaComposing, errors.nameKana?.message]
)

この 3 つ目のブロックには、設計上の判断が入っています。抑制しているのはエラーの表示だけで、保存ボタンの活性（isDisabled: !isValid）には触っていません。

なぜボタンの活性は抑制しないのか

変換中だけ古い isValid を保持すれば、ボタンのちらつきも消せます。しかしそれは、他の欄が invalid な状態でも保存を押せてしまう可能性を作ります。エラー表示は「誤った情報を見せる」ので抑制する価値がありますが、ボタンの活性は常に現在の値に対して正しい。見た目のちらつきより、押せてはいけないボタンが押せる方が重い。だから片方だけ抑制しています。

この欄で踏んだ落とし穴

最初の実装は onBlur だけで変換していました。jsdom のテストは通り、Playwright の fill() でも動いた。しかし実機で日本語入力を使うとまったく変換されませんでした。理由はこの記事の事実 1 のとおりで、IME 経由の入力では確定後に input が来ず、フォーカスを外すまで一度も変換のきっかけが訪れないからです。
jsdom も fill() も composition イベントを出さないので、このバグはテストでは絶対に見つかりません。
