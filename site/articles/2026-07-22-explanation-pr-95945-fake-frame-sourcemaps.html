1. Background

Familiar with RSC Flight errors, fake frames, and patch-error-inspect? Skim to the narrow background, then jump to Intuition.

Deep background — what a stack frame even is here

When JavaScript throws, the runtime builds a stack: a list of function names and file/line/column positions. Developers trust that list. Debuggers click a frame and land on source. Terminal logs print a codeframe under the caret. None of that works unless the engine’s generated positions can be mapped back to the files you wrote — via source maps.

Next.js App Router complicates this. Server Components do not run in the browser. An error may originate in a cache worker, cross into the Flight stream as serialized data, and be revived as a fresh Error object in a different JavaScript realm. The original V8 call stack is gone. What remains is structured debug info that React ships alongside the payload.

Definition · Fake stack frame

A tiny function React builds with eval, padded with newlines and spaces so that calling _() appears at the original line/column. The script is tagged //# sourceURL=about://React/… and usually //# sourceMappingURL=…. When you throw through that chain, Node and debuggers see a real stack that source-maps back to your app.

React’s Flight client materializes those scripts in createFakeFunction. A simplified shape looks like this: 

/* This module was rendered by a Server Component. … */
({"throwsInCache":
        _=>
        _()})
//# sourceURL=about://React/Cache/file%3A%2F%2F%2F…%2Fpage.js?7
//# sourceMappingURL=data:application/json;base64,eyJ2ZXJzaW9uIjozLC4uLn0=

The padding is intentional. The call to _() sits at the same line/column as throw new Error(…) in your source. The source map then tells consumers: “generated line 5, column 9 → app/…/page.js line 5, column 9.”

System diagram · Who consumes the fake-frame source map?

① Node source-map cache

module.findSourceMap learns about eval’d scripts that carry a mapping URL.

② Terminal stacks

patch-error-inspect rewrites Error.prepareStackTrace and prints codeframes.

③ Attached debugger (CDP)

Chrome DevTools Protocol sees Debugger.scriptParsed with sourceMapURL.

All three depend on the same fragile contract: the mapping URL must stay fetchable, and mapped sources must stay well-formed paths — not mangled concatenations like file:/private/var/….

Narrow background — the hole this PR plugs

Pull request #95936 broke symbolication of these fake frames. Existing tests kept passing. The breakage was discovered the hard way: someone attached a debugger and watched source maps fail to load.

That is the classic coverage gap. Message-only assertions (“does the log contain Error: …?”) do not prove that stacks point at the right file with a codeframe, nor that a debugger can resolve sourceMappingURL. Production logs must also avoid leaking the virtual about://React/ scheme into user-facing output.

Why "use cache" is special

An error thrown inside a cache function crosses an environment boundary (Cache → Server (Flight client). The logged error is the one revived by resolveErrorDev, not the original thrown object. Its stack is rebuilt entirely from fake frames. If that revival path loses source maps, you get unhelpful paths or raw virtual URLs — and prior tests did not assert either outcome.

Next.js helps terminal printing in packages/next/src/server/patch-error-inspect.ts. When a frame’s file looks like about://React/…, it devirtualizes the URL before resolving relative sources: 

// packages/next/src/server/lib/source-maps.ts
export function devirtualizeReactServerURL(sourceURL: string): string {
  if (sourceURL.startsWith('about://React/')) {
    // about://React/Server/file://<filename>?42 => file://<filename>
    const envIdx = sourceURL.indexOf('/', 'about://React/'.length)
    const suffixIdx = sourceURL.lastIndexOf('?')
    if (envIdx > -1 && suffixIdx > -1) {
      return decodeURI(sourceURL.slice(envIdx + 1, suffixIdx))
    }
  }
  return sourceURL
}

And in the inspector patch, that real URL is what the source-map consumer uses as a base for relative sources entries: 

// packages/next/src/server/patch-error-inspect.ts (conceptually)
const sourceMapURL = devirtualizeReactServerURL(sourceURL) + '.map'

2. Intuition

Imagine a toy page. One cache function that always throws: 

async function throwsInCache() {
  'use cache'
  throw new Error('rsc-error-throw-cached')
}

export default async function Page() {
  await connection()
  await throwsInCache()
  return null
}

What you want in next dev logs looks like this:

Error: rsc-error-throw-cached at throwsInCache (app/rsc-error-throw-cached/page.js:5:9) 3 | async function throwsInCache() { 4 | 'use cache' > 5 | throw new Error('rsc-error-throw-cached') | ^ 6 | } environmentName: 'Cache'

What a regression can produce instead:

Broken symbolication
at throwsInCache (file:/private/var/…/page.js:5:9) # or worse: at Page (about://React/Prerender/…%5Broot-of-the-server%5D…)
Healthy symbolication
at throwsInCache (app/rsc-error-throw-cached/page.js:5:9) + codeframe pointing at throw environmentName: 'Cache'

Data-flow diagram · Error inside "use cache"

1
Cache environment throws Example data: { name: "Error", message: "rsc-error-throw-cached", stack: [[…]], env: "Cache" }
↓ serialized across Flight
2
resolveErrorDev rebuilds the Error Calls buildFakeCallStack → createFakeFunction → eval of padded script with about://React/Cache/…
↓ consumers look at the revived Error
3a
CLI / patch-error-inspect Devirtualize URL → find source map → print app/…/page.js:5:9 + codeframe
3b
Debugger via CDP Sees Debugger.scriptParsed { url: "about://React/…", sourceMapURL }; frontend loads the map (data URL, file, or Network.loadNetworkResource)

The core intuition of the PR is simple: assert the contract at every consumer. Do not only check that an error message appears. Check that (1) terminal stacks are fully symbolicated with codeframes, (2) a real debugger attachment can resolve every fake-frame source map and map the padded _() call back to the fixture file, and (3) production never prints raw about://React/ URLs.

3. Code walkthrough

This PR touches four files, all under test/. No production runtime changes. We will walk them in the order that builds understanding: fixture → terminal assertion → restored validation assertion → CDP harness.

3.1 New fixture: throw inside "use cache"

File: test/e2e/app-dir/server-source-maps/fixtures/default/app/rsc-error-throw-cached/page.js 

import { connection } from 'next/server'

async function throwsInCache() {
  'use cache'
  throw new Error('rsc-error-throw-cached')
}

export default async function Page() {
  await connection()
  await throwsInCache()
  return null
}

await connection() opts the route into dynamic rendering so the cache call actually runs at request time. The throw is the whole point: it forces the Flight revival path (resolveErrorDev) rather than a same-realm stack.

3.2 Assert the symbolicated CLI stack

In server-source-maps.test.ts, a new test renders that page and checks two different contracts depending on mode:

  • Dev: full stack + codeframe pointing at the throw, and environmentName: 'Cache' proving the logged error is the revived one.
  • Prod (next start): runtime stacks are not fully sourcemapped, but output must not contain about://React/. 
it('thrown errors from "use cache" have a sourcemapped stack with a codeframe', async () => {
  if (isNextDev) {
    await next.render('/rsc-error-throw-cached')
    // … wait for Error: rsc-error-throw-cached …
    expect(cliOutput).toContain(
      'Error: rsc-error-throw-cached' +
        '\n    at throwsInCache (app/rsc-error-throw-cached/page.js:5:9)' +
        // … codeframe …
    )
    expect(cliOutput).toContain("environmentName: 'Cache'")
  } else {
    // prod: no leak of virtual URLs
    expect(normalizeCliOutput(/* … */)).not.toContain('about://React/')
  }
})
What this would have caught in #95936

Broken runs showed frames like at throwsInCache (file:/private/var/…) or ../-prefixed paths — substring checks on the message alone would still pass.

3.3 Restore a previously weakened assertion

In cache-components-dev-errors.test.ts, a blocking-route validation error used to assert the full CLI stack + codeframe. That was reduced to a docs-link / message check in an earlier commit. This PR puts the stack assertion back: 

expect(stripAnsi(next.cliOutput.slice(outputIndex))).toContain(
  '\n    at Page (app/no-accessed-data/page.js:2:9)' +
    '\n  1 | export default async function Page() {' +
    '\n> 2 |   await new Promise((r) => setTimeout(r, 200))' +
    '\n    |         ^' +
    '\n  3 |   return <p>Page</p>' +
    '\n  4 | }'
)

Those stacks flow through Prerender-environment fake frames. When symbolication broke, frames leaked bracket-encoded chunk names and raw about://React/…%5Broot-of-the-server%5D… URLs.

3.4 The new CDP test — act like a debugger

File: fake-frame-source-maps.test.ts (~349 lines). This is the novel piece. It starts the app with the first-class --inspect=0 flag (works for both next dev and next start), finds the server’s inspector WebSocket, and speaks Chrome DevTools Protocol.

Flow · CDP test (dev path)

1
Boot with startArgs: ['--inspect=0'] Node prints Debugger listening on ws://127.0.0.1:<port>/
2
Render /rsc-error-log React materializes fake frame scripts for Server Component debug info
3
Debugger.enable Collect every scriptParsed whose URL starts with about://React/
4
resolveSourceMapLikeADebugger data: → decode base64 · relative/file: → read disk · http(s): → Network.loadNetworkResource through the target
5
Map the padded _() call Use Node’s SourceMap class; assert a well-formed source that includes the fixture page

Why load http(s) maps through the debugged target? Because the dedicated Chrome DevTools frontend for Node targets does not freely fetch arbitrary remote URLs itself. Reproducing that constraint is the point — when #95936 broke network resource loading, the failure message matched what a human debugger saw: “Unable to load source map through the debugged target” / “Network resource loading is not enabled…”.

The prod branch of the same file is slightly different: instead of mapping fake about://React/ scripts, it asserts that .next/server/… chunk scripts declare resolvable source maps, and that the rendered page’s original source appears in sources (exact match differs for Turbopack vs webpack).

Well-formedness guard

expectWellFormedSource requires sources to match /^(file:\/\/\/|turbopack:\/\/|webpack:\/\/)/. That catches mangled concatenations like file:/cwd-relative/path which naïve substring assertions would miss.

3.5 How the pieces fit together

  • Fixture creates the hard case (cache → Flight → revive).
  • CLI assertion locks the developer-facing terminal contract.
  • Restored validation assertion covers Prerender-environment fake frames.
  • CDP harness locks the debugger-facing contract that humans hit manually.

Together they answer the question #95936 left open: “If we break fake-frame source maps again, will CI fail for the same reason a debugger fails?” Yes.
