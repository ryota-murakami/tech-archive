TypeScript conditional type

この型は「同じ型か」を見ていない

RoundTrippableSchema は、スキーマを二つの問いでふるいにかける。入力が unknown か any なら捨てる。そうでなければ、出力を入力に渡せるかを見る。通ったスキーマはそのまま残り、落ちたスキーマは never になって、関数の引数に渡せなくなる。

Background

先に、この型が立っている地面を二つだけ敷く。条件型の読み方と、Zod が「入る型」と「出る型」を分けていること。どちらも知っている人は Intuition へ進んでよい。

条件型の extends は代入できるか、という問い

TypeScript の条件型は SomeType extends OtherType ? TrueType : FalseType と書く。JavaScript の三項演算子に見えるが、実行時には消える。残るのは型だけだ。左の型が右の型へ代入できるとき真の枝、できないとき偽の枝を選ぶ。公式ハンドブックの言い方はそのまま「assignable」である（Conditional Types）。

type Example1 = Dog extends Animal ? number : string; // number
type Example2 = RegExp extends Animal ? number : string; // string

ここでの extends は「クラスの継承」ではない。number extends number | string は真になる。数は「数または文字列」に代入できるからだ。逆の number | string extends number は偽になる。文字列が混ざった値を、数だけの場所には置けない。

分配（distributive）になるのは、検査される側が裸の型引数のときだけだ。T extends U ? X : Y に string | number を入れると、メンバーごとに計算して結果を足し直す。左右を [T] extends [U] のようにタプルで包むと、その分配は止まる（同じハンドブックの Distributive Conditional Types）。今回の型の左側は unknown と z.output<Schema> であり、裸の Schema ではない。

unknown は、自分自身と any にしか代入できない TypeScript 3.0 で入った unknown は、あらゆる値を受け取れる頂上の型だ。ただし unknown 自体を他の型の変数に入れることは、unknown と any 以外ではできない（TS 3.0 release notes）。だから unknown extends T は、「T は unknown か any か」という検査になる。逆向きの T extends unknown は、T が何であっても真になる。何でも unknown に入るからだ。

Zod は入力と出力を別の型として持っている

このリポジトリの Zod は 4.6.2 だ。スキーマの土台は ZodType<Output = unknown, Input = unknown> で、出力も入力も初期値は unknown である（node_modules/zod/v4/classic/schemas.d.ts の 7 行目）。取り出すユーティリティは次のとおりで、定義は node_modules/zod/v4/core/core.d.ts の 53–63 行にある。z.infer は出力の別名だ。

export type input<T> = T extends { _zod: { input: any } }
  ? T["_zod"]["input"]
  : unknown;
export type output<T> = T extends { _zod: { output: any } }
  ? T["_zod"]["output"]
  : unknown;
export type { output as infer };

変換がないスキーマでは、二つは同じ型になる。z.string() の入力も出力も string だ。変換があると割れる。公式の例は z.string().transform((val) => val.length) で、入力は string、出力は number である（zod.dev/basics）。z.coerce.number() の入力は、型引数を付けなければ unknown、出力は number だ。z.coerce.number<number>() と書くと入力も number に狭まる（zod.dev/api、この環境の 4.6.2 で同じ結果を確認した）。

get が返すのは出力、set が受け取るのは入力、という対応が、この型の存在理由になる。読んだ値を、もう一度書けるか。それが「往復できる」の中身だ。

Intuition

関数の引数はこうなっている。

schema: Schema & RoundTrippableSchema<Schema>

Schema は、渡したスキーマから推論される。その横に、同じ Schema を条件型に通した結果を交差で重ねる。条件型が Schema 自身を返せば、交差はスキーマのまま残る。条件型が never を返せば、交差は never になる。never には何も代入できないので、その呼び出しはコンパイルエラーになる。エラーメッセージは「never に代入できない」であり、「往復できません」とは書かない。ふるいは型の底に穴を開けて、落ちた引数をそこへ落とす。

二つの扉 — 通れば Schema、落ちれば never

扉 1　unknown extends z.input<Schema> 入力は unknown か any か。真なら never。set が何でも受けてしまうスキーマをここで止める。
扉 2　z.output<Schema> extends z.input<Schema> 出力は入力に代入できるか。偽なら never。get の結果を set に渡せないスキーマをここで止める。
両方を抜けたら Schema 交差しても型は変わらない。呼び出しは通る。
どちらかで落ちたら never Schema & never は never。引数の位置が never になり、実スキーマはそこに乗らない。

おもちゃで、扉の仕事が違うことを見る。どちらも「入力と出力が違う」が、止まる扉は別だ。

同じ「型が違う」でも、止まっている扉が違う

z.coerce.number()

  • 入力 unknown、出力 number
  • 扉 1 が真なので never
  • 扉 2 だけなら通る。number は unknown に入る

z.string().transform(Number)

  • 入力 string、出力 number
  • 扉 1 は偽。入力は string であって unknown ではない
  • 扉 2 が偽。number は string に入らない

通る変換もある。z.union([z.number(), z.string()]).transform(Number) の出力は number、入力は number | string だ。数は「数または文字列」に代入できる。get が返した 5 を、set に戻せる。文字列から数への変換そのものが禁止されているわけではない。

ソースの直前コメントは「入力と出力が同じ型のスキーマのみ」と書いている。測定すると、その説明には余白がある。z.string().default("x") の入力は string | undefined、出力は string で、同じではない。それでも string は string | undefined に入るので、この型は受け付ける。見ているのは同一性ではなく、出力から入力への代入だ。

Mechanics

以下の表は、このリポジトリの TypeScript 6.0.3 と Zod 4.6.2 で、コンパイラ API の typeToString に型を渡して読んだ結果だ。条件型の定義はソースの複製ではなく、読み取り対象の式そのものを評価している。

扉 1 は「入力が頂上型か」

式は unknown extends z.input<Schema>。測定した素の関係はこうだった。

検査結果
unknown extends unknownyes
unknown extends anyyes
unknown extends stringno
string extends unknownyes（何でも真なので、この向きはふるいにならない）

だから z.unknown() も z.any() も扉 1 で落ちる。ここが無いと、扉 2 だけではどちらも通る。測定では、扉 2 だけを z.output extends z.input として適用すると、z.any() も z.unknown() も z.coerce.number() も真の枝になった。coerce の出力 number は、入力 unknown に代入できる。幅が広すぎる入力を止める仕事は、扉 1 にしかない。

z.coerce.number<number>() は入力が number なので扉 1 を通る。出力も number なので扉 2 も通り、結果は受理だった。コメントが「coerce を使うと弾く」と読める箇所は、型引数なしの初期入力 unknown の話だ。入力をピンした coerce は、この型は止めない。

z.preprocess も同じ構造で、第二型引数の初期値は unknown である（schemas.d.ts 818 行、ZodPreprocess<B, I = unknown> は 719 行）。(value: unknown) => value を渡すと入力は unknown のまま落ちる。(value: string) => value.trim() のように引数を string へ注釈すると、入力も出力も string になり、受理された。

any を条件型の左に置くと、両枝が混ざることがある 測定では any extends string ? "yes" : "no" が "yes" | "no" になった。一方 any extends any を同じ形で聞くと、真の枝だけが残った。扉 2 が z.any() を通してしまうのは、この「両枝ユニオン」のせいではなく、頂上型どうしの代入が真になるせいだ。いずれにせよ扉 1 が先に never へ落とす。

扉 2 は「読んだ値を、もう一度書けるか」

式は z.output<Schema> extends z.input<Schema>。真なら Schema、偽なら never。返しているのは true ではない。スキーマ型そのものだ。ここは後で交差の話に戻る。

z.string().transform(Number) は、出力 number が入力 string に入らないので落ちる。オブジェクトで包んでも同じで、{ page: number } は { page: string } に入らない。測定したエラーは次の形だった。シグネチャをこの型のまま複製し、同じ TypeScript で tsc にかけた結果である。

error TS2345: Argument of type
  'ZodObject<{ page: ZodPipe<ZodString, ZodTransform<number, string>> }, $strip>'
  is not assignable to parameter of type 'never'.

z.coerce.number() は ZodCoercedNumber<unknown>、z.any() は ZodAny、z.preprocess(..., unknown) は ZodPreprocess<ZodString, unknown> として、同じ「never に代入できない」で止まった。

真の枝が Schema を返す理由

交差の相手が true だと、通ったスキーマまで落ちる。測定では z.ZodString & true は never に簡約されなかったが、z.ZodString はその交差へ代入できなかった（"not assignable"）。つまり真の枝を true にすると、健全な z.string() まで引数に乗れなくなる。

真の枝が Schema なら、typeof stringSchema & typeof stringSchema は z.ZodString のまま残った。偽の枝の never は、typeof stringSchema & never を never に潰した。受理は恒等、拒否は底、という交差のための戻り値だ。

定義 Schema & RoundTrippableSchema<Schema> は、推論で具体スキーマを掴んでから、そのスキーマに条件を掛ける書き方だ。条件を先に制約位置へ置くと、まだ決まっていない Schema を条件型が参照して推論が回りにくくなる。引数の交差は、推論のあとで穴を開ける。

この型が見ないもの

z.date() は入力も出力も Date なので、この型は受理する。JSON は別だ。この環境で JSON.stringify({ at: new Date("2026-10-05T00:00:00+09:00") }) は {"at":"2026-10-04T15:00:00.000Z"} になり、JSON.parse した at の typeof は "string" だった。z.object({ at: z.date() }).safeParse はその値を拒否した。z.union([z.date(), z.iso.datetime()]) に new Date(value) を噛ませたスキーマは通り、at は Date に戻った。型が保証するのは「出力の型が入力の型に入る」ことまでで、JSON にしたあとの形までは見ない。

もう一つ、条件型は分配していない。単独では落ちる z.string().transform(Number) と、通る z.number() をユニオンにした型は、測定では受理だった。入力は string | number、出力は number、number extends string | number が真になる。メンバーごとに扉を通しているのではなく、ユニオンを一つの型として見ている。呼び出しの推論は通常、渡した一つのスキーマ式の型になるので、この穴は「スキーマのユニオン型を変数に入れて渡したとき」に開く。

フィールドを足す transform も通った。{ name: string; length: number } は { name: string } に代入できる。構造的型付けでは、余分なプロパティがあっても extends は真になる。これは get の結果を set に渡せる、という検査の帰結でもある。

In this codebase

定義は src/functions/localStorageHandler.ts の 256–261 行にある。直前のコメントは 254–255 行で、「入力と出力が同じ型だけに限定する」「z.coerce / z.preprocess は異なる型になるので never で弾く」とある。測定と突き合わせると、コメントは意図の要約で、式そのものより狭い。式は同一性ではなく二段の代入検査で、coerce を止めるのは「型が異なるから」ではなく「初期入力が unknown だから」だ。

type RoundTrippableSchema<Schema extends z.ZodType> =
  unknown extends z.input<Schema>
    ? never
    : z.output<Schema> extends z.input<Schema>
      ? Schema
      : never;

使われるのは 266–268 行の defineObjectStorage だけだ。get の戻り値は z.output<Schema> | undefined（272 行）、set の引数は z.input<Schema>（302 行）。条件型は、その二つの型のあいだに「出力を入力へ戻せる」を要求する。保存前の JSON 往復は型ではなく 300–319 行の set が実行時に行う。そこで z.date() のような、型は通るが JSON にすると文字列になる値が落とされる。

型だけの検査は src/functions/localStorageHandler.spec.ts の 12–22 行にある。@ts-expect-error が二つある。

  • z.object({ page: z.string().transform(Number) }) — 扉 2。コメントは「出力 number を入力 string に戻せない」。
  • z.coerce.number() — 扉 1。コメントは「入力が unknown になり set が何でも通る」。

同じファイルの実行時テストは、型が通す z.union([z.number(), z.string()]).transform(Number) と、型が通す z.date() を両方置いている。前者は保存して読める。後者は set が保存を拒否する。型と実行時の分業が、テストの配置に出ている。

最初の本番スキーマは src/functions/local_storage/newCompanySettingStorage.ts だ。z.enum(LOCALE_MASTER_IDS) のように、入力と出力が同じ列挙のオブジェクトだけを渡している。測定した z.enum(["japanese", "english"]) と同じ形で、両方の扉を素通りする。
