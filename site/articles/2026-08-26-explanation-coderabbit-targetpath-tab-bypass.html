背景

この PR を理解するには、まず「ログイン後の戻り先」という、どのアプリにもありそうで、 しかし驚くほど事故を起こしやすい仕組みを知る必要がある。

深い背景 — 「ログイン後の戻り先」とは何か（この分野に馴染みがあれば飛ばして構わない）

あなたが同僚から図面のリンクを受け取ったとしよう。https://zume-n.com/drawings/80000 をクリックする。 しかしログインしていないので、アプリはあなたをログイン画面へ送る。ログインを終えたあと、 どこへ着地すべきだろうか。

トップページに放り出されたら、あなたはもう一度リンクを探しにメールへ戻ることになる。 親切なアプリは「あなたが本当は /drawings/80000 を見たかった」ことを覚えておき、 ログイン後にそこへ連れて行く。この「覚えておく値」を、このアプリでは targetPath と呼び、ブラウザの localStorage に保存している。

① 保存 ログインが必要な画面に未ログインで来た時、その URL を書き込む
→
② 保管 localStorage に残る。ログアウトしても消えない設定になっている
→
③ 消費 ログイン成功後に読み出し、そこへ遷移して、値を削除する
用語

消費地点とは、③ の「読んで・使って・消す」場所のこと。切符と同じで、一度使えば無くなる。 本文では「保存地点」（①）と対にして使う。

さて、ここに落とし穴がある。localStorage はブラウザの持ち主なら誰でも書き換えられるし、 ①の保存はユーザーが開いた URL をそのまま写し取る。つまり targetPath の中身は、アプリから見れば信用できない外部入力だ。 そして③で、その値を使って遷移する。信用できない値で遷移する——これは オープンリダイレクトという古典的な脆弱性の型そのものである。

典型的な攻撃は、値を //evil.example にすることだ。先頭が / なので 「サイト内の絶対パス」に見える。ところがスラッシュ 2 つで始まる URL は プロトコル相対 URL と呼ばれ、ブラウザは「今と同じ http/https で、evil.example という別のサイトへ」 と解釈する。ログインした直後の、最も警戒心が緩んだ瞬間に見知らぬサイトへ飛ばされることになる。

だから③の手前には検問がある。それがこの PR の主役、checkIsInAppPath という関数だ。

直接の背景 ① — 招待 URL が顧客のログインを乗っ取った事件

2026 年 8 月、本番環境で実際の障害が起きた。社内向け Google SSO の招待メールのリンク—— /admin/login?invitation=...——を一度開いたブラウザで、後日まったく別の顧客アカウントに パスワードでログインすると、企業選択のあとでその招待 URL へ飛ばされ、 ログイン画面との間を無限に往復するというものだった。

原因は、招待 URL が targetPath に保存され、ログアウトを生き延び、 後日の別人のログインで消費されたことにあった。修正は 2 段構えで行われた。

hotfix #4215 の 2 段構え

  • 予防（保存地点）: 除外リストに /^\/admin\// を足し、招待 URL をそもそも保存させない。
  • 治療（消費地点）: 同じ除外判定を消費地点でも使い、すでに汚染済みのブラウザが次のログインで自力回復できるようにする。

このとき明確に決められた原則がある——「消費側に別の判定を書かないこと」。 判定が 2 系統になると、次に画面が増えたとき片方だけを更新して、もう片方が腐るからだ。 この原則は、後で CodeRabbit の提案を却下する根拠になる。

直接の背景 ② — 移設で片方だけが落ちた

ところがこの hotfix は stg ブランチ上で作られ、開発中の dev ブランチには 別途取り込む必要があった。そして dev では、ちょうど SSO ph2 の作業で src/functions/targetPath.ts が src/libs/auth0/targetPath.ts へ移設されていた。 さらに消費地点そのものも、別のコンポーネントへ引っ越していた。

結果として dev に取り込まれたのは予防（保存側）だけで、治療（消費側）が落ちた。 それを埋め直すのが、この PR #4231 の当初の目的である。

核心 — 検問は、通る本人を見ていなかった

CodeRabbit の指摘を一言でいえばこうだ。私たちが検査した文字列と、ブラウザが遷移先として使う文字列が、 別物だった。

2 人の読み手が、同じ紙を違うように読む

検問は「タブを含んだ生の文字列」を見て合格を出した。しかし遷移に使われるのは 「ブラウザがタブを取り除いたあとの文字列」だ。審査した書類と、実際に提出された書類が違う。 検問が甘かったのではなく、検問が見ていた対象が間違っていた。

これは URL 標準（WHATWG URL）の仕様どおりの挙動である。URL を解析する最初の手順が 「入力からすべての ASCII タブと改行を取り除く」と決まっている。位置は問わない——先頭でも、真ん中でもだ。 実際に Node.js の URL 実装で、先頭 / の直後に制御文字を 1 つずつ入れて確かめると、 行き先のサイト（origin）が変わってしまうのは次の 3 文字だけだった。

同じタブでも、パーセント符号化された %09 は取り除かれない。 /%09/evil.example は最後まで自サイトのパスのままで、危険はない。 「生のタブ」と「符号化されたタブ」はまったく別物である——この違いは後のクイズにも出てくる。

CodeRabbit が提案した修正はこうだった。「消費地点で new URL を使って正規化し、 origin を検証したうえで、正規化後の pathname・search・hash を除外判定に渡せ」。 技術的には正しく効く。しかしこの PR では採用しなかった。

採った修正

すり抜けの原因である共通関数 1 箇所に、タブ・改行を含む値を丸ごと拒否するガードを足した。 正当なサイト内パスにこれらの文字が生で入ることはない（本来 %09 等に符号化される）ので、 正しい値を巻き込む心配もない。 

export const checkIsInAppPath = (path: string): boolean =>
  /^\/[^\/\\]/.test(path) && !/[\t\n\r]/.test(path);
//                                 ↑ 追加したのはこれだけ

では、これは「炎上案件」だったのか — 到達可能性の話

指摘が技術的に正しいことと、それが今すぐ本番を止めるべき緊急事態であることは、別の問題だ。 ここは冷静に分けて考える必要がある。

攻撃が成立するには、生のタブを含む値が targetPath に保存されなければならない。 保存元をたどると、値の出どころは router.asPath——つまり ブラウザがすでに解析を終えた後の URL——ただ一つである。

攻撃者がタブ入り URL を踏ませようとすると何が起きるか
罠のリンクhttps://zume-n.com/⇥/evil.example
→
ブラウザが解析この時点でタブが消える
→
evil.example へ直行アプリのコードに到達しない
→ タブはアプリに届く前に消えるため、保存処理がタブ入りの値を受け取る経路が存在しない。
結論：深層防御の穴であって、悪用可能な脆弱性ではない

残る侵入経路は「本人が DevTools で localStorage に手で書き込む」（＝自分で自分を攻撃する）か、 別途 XSS が存在する場合だけで、後者ならそもそももっと深刻な問題が起きている。 したがってこれは直すべきだが、本番を止めて緊急リリースする性質のものではない。

レビュー指摘に向き合うときの型として、これは覚えておく価値がある—— 「指摘の事実が真か」と「提案された修正を採るか」と「どれだけ急ぐか」は、それぞれ独立に判定する。 今回は「事実は真 / 提案は不採用 / 緊急性は低い」という組み合わせだった。

コミット 1 — 欠けていた検問を足す 57e1f5834

dev の消費地点 RequireCompanyId に、hotfix の「治療」半分にあたる checkIsExcludedPath を追加した。ここまでは CodeRabbit 以前の話である。

コミット 2 — 三項演算子から ts-pattern へ dc134918b

条件が 3 つ重なった時点で、三項演算子の連なりは「どの条件で何が起きるのか」を読み取りにくくする。 match に開くと、分岐ごとに理由をコメントで添えられる。 stg/main 側の同じ処理もすでにこの形になっていたので、両者の見た目が揃った。 

const nextPath = match(targetPath)
  // 戻り先が保存されていない。ログイン画面から普通にログインするとここに来る
  .with(P.nullish, () => CUSTOMER_LOGIN_REDIRECT_PATH)
  // `//evil.example` や `/\evil.example` のように別サイトを指す値。
  // localStorageは誰でも書き換えられるので、そのまま遷移させない
  .when(
    (path) => !checkIsInAppPath(path),
    () => CUSTOMER_LOGIN_REDIRECT_PATH
  )
  // 社内向けの招待URL(/admin/login?invitation=...)やログイン画面など、
  // 顧客が戻るとログインが終わらなくなる画面
  .when(checkIsExcludedPath, () => CUSTOMER_LOGIN_REDIRECT_PATH)
  // QRコードや共有リンクで開いた図面詳細など、ログイン前に見ようとしていた画面
  .otherwise((requestedPath) => requestedPath);
読みどころ

この並び順が、後の防御に効いている。checkIsInAppPath の判定が 除外判定より先にあるため、コミット 3 でここにガードを足すと、 タブ入りの招待 URL（被害 B）は除外判定にたどり着く前に倒れる。

指摘された 2 ケースをそのままテストにした。ただしテストを足すだけでは、 そのテストが本当にこの修正を守っているのかは分からない。 そこで追加したガードだけを取り外して、テストが落ちることを実測した。

後日談 — 「もう 1 か所にも同じ穴が」の落とし穴

この修正のあと、もう一つ間違いがあった。それも記録しておく価値がある。

checkIsInAppPath は、stg/main 側にも src/functions/targetPath.ts という別ファイルとして同じ実装が残っている。 だから最初、こう申し送った——「stg/main 側にも同型の穴があるので、別途 hotfix が必要です」。

しかしこれは誤りだった。SSO ph2 のリリース（dev → stg → main → release）には、 そのファイルを削除する移設そのものが含まれている。 実際に git merge-tree でマージ後のツリーを作って中身を確かめると、こうなった。

確認項目実測結果
コンフリクト0 件
Ph1 の src/functions/targetPath.ts（穴あり）マージ後のツリーから削除される
残る実装src/libs/auth0/targetPath.ts のみ・ガード込みで生存

つまり通常のリリースフローに乗せるだけで解消し、別 hotfix（PR 3 本＋リリース調整）は まるごと不要だった。前節の「到達可能性」と合わせれば、急ぐ理由も無い。

教訓

「別ブランチにも同じ穴がある」と申し送る前に、マージフローでそのファイルが生き残るのかを実測する。 ファイル移設を含むリリースでは、穴のある側がファイルごと消えることがある。 不在の主張（「まだ塞がっていない」）は、存在の主張よりも検証が要る。
