1. 背景 — 既存システムを知るこの PR が触るのは「組図タブ」「job_statuses」「GCS」「React Flow」「Jest」の 5 領域。順に足場を固める

1.1 初学者向け: 組図・ツリー・ジョブ・署名付き URL

ズメーンの組図タブと job_statuses 系の非同期処理を知っている人は 1.2 へ飛んでよい。

組図 (アセンブリ) とは

製造業の図面は「本体」の下に「ユニット」があり、その下に「部品」がある、という入れ子で管理される。ズメーンではこの親子関係を組図 (assembly) と呼び、図面詳細画面の組図タブで横向きのツリーとして表示する。1 つの図面は複数の親を持てる (共通部品が 2 つのユニットにぶら下がる) ので、厳密には木ではなくグラフだが、1 つの最上位図面から見れば木として描ける。

BE はこの構造を drawing_connections テーブル (drawing_id, parent_id, 並び順) で持ち、FE は GET /drawings/{id}/assembly_graph で最上位図面を根にした入れ子の JSON を受け取る。

組図の編集はどうやっていたか

この PR より前、組図の階層を変える手段は組図タブの「階層編集」モードでのドラッグ & ドロップだけだった。保存は PATCH /drawings/{id}/assembly_graph に { children: [{ id, children: [...] }] } という入れ子の ID だけを送る。BE はこれを受けて、その最上位図面の配下を丸ごと置き換える (全置換)。差分ではなく「これが正しい全体だ」を送る API なので、送り忘れた子は消える。この性質があとで大事になる。

job_statuses 系の非同期ジョブ

時間のかかる処理 (PDF 分割、CSV エクスポートなど) は、HTTP リクエストの中で終わらせず、BE がジョブとして Laravel Queue に積む。FE は起票 API から job_status_id を受け取り、GET /job_statuses/{id} を数秒おきに叩いて (ポーリング) status が queued → executing → finished | failed と進むのを見る。成果物 (ファイル) がある場合は GET /job_statuses/{id}/download_signed_urls で取り出し口をもらう。

署名付き URL と GCS

ファイル本体は BE のサーバーを通さず、Google Cloud Storage (GCS) と直接やり取りする。BE は「この URL になら 1 時間だけ PUT (または GET) してよい」という署名付き URL を発行し、FE は素の axios でその URL にアクセスする。つまりアップロードは「BE に署名付き URL をもらう → GCS に PUT → BE に file_key を渡す」の 3 手になる。既存の useUploadFilesToGcs がこの 3 手を隠している。

key concept 署名付き URL への通信は axiosClient の interceptor (失敗トースト・New Relic 送信) を通らない。GCS 直アクセスの失敗は、機能側が自分で New Relic に送る必要がある。この PR のあちこちに captureException があるのはそのため。

React Flow

組図タブのツリーは @xyflow/react (React Flow v12) で描いている。ノードは自前の React コンポーネント、エッジ (線) は step 形。位置は React Flow が決めてくれるわけではなく、自分で x, y を計算して position に書く。そのためにノードの実寸 (measured.width/height) を React Flow が測ってくれるのを待ち、揃ったところでレイアウト関数を走らせる、という段取りが既存の useAutoLayout にある。

Jest と TanStack Query

このリポジトリの Jest セットアップ (src/tests/common.ts) は @tanstack/react-query をモジュールごとモックしている。普通のコンポーネント spec には都合がよいが、「mutation が成功したら query が動き始め、その結果で別の query が動く」という連鎖を検証するには本物の react-query と、HTTP を返してくれる偽 BE が要る。この PR はそこに MSW (Mock Service Worker) を持ち込んだ。

1.2 この変更に直接効く前提

Backlog が決めた体験

  1. 組図タブの三点リーダーに「エクセルで階層を組み替え」が出る。条件は組図の編集権限があること、対象図面が最上位であること。
  2. モーダルで「1. 編集用エクセルをダウンロード」「2. 編集したファイルをアップロード」の 2 ステップ。xlsx のみ、5MB まで、1 ファイル。
  3. アップロードは BE で照合 (matching) というジョブになる。エクセルの各行を「図番・品名・区分…」で既存組図内の図面と突き合わせ、行ごとに 確定済み / 候補が複数 / 候補なし の 3 状態にする。
  4. バリデーションエラーがあれば結果ではなくエラーレポート CSV が返り、ユーザーはそれをダウンロードして閉じる。
  5. 照合が通れば「階層の確認・編集」モーダルが開く。未確定 (候補が複数 / 候補なし) を全部解消しないと保存できない。解消の手段は「候補から選ぶ」「図面を選択」「組図から除外」。
  6. 保存は既存の全置換 PATCH。ポーリングは最大 180 秒で諦める。

2. 直感 — 何を、どう組み立てたか細部は 3 章に譲り、ここでは 6 つの芯だけを具体例で押さえる

2.2 「時計」を誰が進めるか

180 秒で諦める、という要件は簡単そうに見えるが、素直に setTimeout を置くと React の再マウント・タブの非アクティブ化・ネットワーク断で壊れる。この PR はポーリングの応答が返った時刻を時計にした。TanStack Query は成功応答の時刻を dataUpdatedAt、失敗確定の時刻を errorUpdatedAt に持つので、その大きい方を「最後に settle した時刻」とみなす。

// deriveAssemblyExcelImportPhase.ts
export const getLastSettledAt = (state) => Math.max(state.dataUpdatedAt, state.errorUpdatedAt);

const checkIsPollingTimedOut = (state, pollingStartedAt) =>
  getLastSettledAt(state) - pollingStartedAt >= ASSEMBLY_GRAPH_MATCHING_POLLING_TIMEOUT_MS; // 180_000

ただしこの時計には穴が 2 つあり、どちらもレビューで塞いだ。

  • 応答が返らないと時計が止まる。BE がハングすると dataUpdatedAt も errorUpdatedAt も進まない。そこで 1 回の GET に timeout: 10_000 を付け、10 秒ごとに必ず「失敗」として settle させる。
  • retry 中は errorUpdatedAt が更新されない。TanStack Query は retry を続けている間、query を pending のまま保つ。「ETIMEDOUT なら無限に retry」と書くと時計が永遠に進まない。そこで retry 述語の先頭で Date.now() - pollingStartedAt >= 180_000 なら false を返し、そこで初めて query を error に落として局面を failed (polling_timed_out) に進める。
≥ 180s → 期限切れ
起票t=0
executingt=3s
executingt=6s
10s timeoutt=19s 失敗で settle
executingt=22s 復旧
finished + resultt=…
180s諦める
応答が返るたびに時計が進む。10 秒のリクエスト timeout があるので、BE が黙っても 10 秒に 1 回は進む。終端 (finished / failed) の応答は 180 秒ちょうどに届いても捨てない (終端判定を期限判定より先に置く)。

ポーリングを止めるのも同じ関数群がやる。useQuery の enabled に関数を渡し (enabled: (query) => checkShouldContinuePolling(query.state, pollingStartedAt))、終端・error・期限切れのどれかに着いたら false を返す。enabled: false になった query は、タブを切り替えても、ネットワークが復帰しても再取得しないので、一度 failed になった表示が勝手に成功に戻ることがない (sticky)。

2.4 保存は既存の全置換 PATCH に流し込む

保存ボタンは serializeAssemblyHierarchyDraftForSave(result, overrides) で下書きを PATCH のボディに直列化する。除外行は配下ごと落とし、選択済み行は選んだ id に置き換える。上の例なら次の 1 行になる。

{ parentDrawingId: 53, children: [ { id: 201, children: [] } ] }   // 行 4 (除外) は消えている

ここで 1.1 の「全置換」が牙を見せる。組図タブには「新規図面を追加と同時に組図に紐づける」というアップロードのバックグラウンド処理があり、アップロードが終わった順に子を組図へ書き込んでいく。確認モーダルを開いている数分の間にその処理が子を足していたら、いま送る全置換ボディはその子を知らないので消してしまう。

だから保存は、既存の階層編集モードの保存 (useChangeMode.onClickSave) と同じ 3 段の手順を通す。

1. 直列キューに入るrunExclusiveAssemblyGraphWrite。バックグラウンド紐づけと同時に PATCH しないための順番待ち
→
2. 消してはいけない子を補うappendUploadedChildrenMissingFromSavedTree。紐づけ済みなのに送るツリーに無い子を末尾に足す。ただし removedChildDrawingIds に入っている図面は「ユーザーが外した」と見て足さない
→
3. PATCH → 記録 → 再取得PATCH /drawings/53/assembly_graph → reconcileAssemblyUploadGroupsAfterEditSave → invalidateAssemblyDrawingQueries → トースト → 全モーダルを閉じる
2 段目の removedChildDrawingIds には、除外配下で落ちた図面と「組図から外れる図面」の両方を渡す。レビューで見つかったバグ: 外れる図面を渡していなかったため、直前のアップロードで紐づいた図面をエクセルで外しても、自己修復がツリーに戻してしまう可能性があった。

2.5 サムネイルは id で受け取り、FE が束ねて解決

確定済みノードにはサムネイルを出す。当初 BE は結果 JSON の各図面に署名付き thumbnail_url を埋める予定だったが、GKE 上での署名は 1 件ごとに IAM への HTTPS 往復になり、実データ最大 4,311 図面では 180 秒のジョブ時間を食い尽くす見積りだった。加えて署名付き URL は 1 時間で切れるので、数百図面の確認作業が長引くと画像が壊れる。

そこで契約を変えた。BE は drawing_file_id (図面の先頭ファイルの id、整数) だけを返し、FE が既存の GET /drawing_files/urls?drawing_file_ids[]=… で URL に解決する。この API は既に「20 件ずつ」「10 分キャッシュ」で図面一覧のサムネイルに使われている。

問題は呼び方だ。各ノードが自分の id を 1 件ずつ要求すると、画面に 30 ノードあれば 30 リクエストになる。逆に画面側で id 配列を組み立てると、React Flow のノード (props を受け取れない) から可視ノードの集合を吸い上げる配線が要る。この PR は per-id の useQuery + モジュール内のバッチローダーという DataLoader 風の作りにした。

2.6 ツリーの並べ方を純粋関数に切り出す

確認モーダルのツリーは、組図タブと同じ「左から右へ階層、同じ階層は上に詰めて積む」見え方にする。既存のレイアウトは useHorizontalTopStickyLayoutAlgorithm (約 330 行) の中で、React Flow のノード型・図面データ・「図面を選択」プレースホルダの都合と混ざっていた。この PR はそこから位置計算だけを layoutTreeHorizontalTopSticky という純粋関数に抜き出し、既存側はそれを呼ぶ 60 行のアダプタになった。

// 入力はレイアウトに要る最小限だけ。React Flow の型を知らない
type TreeLayoutNode = { id: string; hidden?: boolean; measured?: { width?: number; height?: number }; sort: number; isPlacedLast?: boolean };

const positions = layoutTreeHorizontalTopSticky({ nodes, edges, horizontalIntervalPx: 396, verticalMarginPx: 24 });
positions.get('matching:3')  // => { level: 1, sort: 0, x: 396, y: 0 }

アルゴリズムは 2 パス。pass 1 で可視ノードだけの木を作り、各部分木が使う階層の集合を持つ。pass 2 で深さ優先に y を決める。先頭の子は親と縦中央を揃え、2 番目以降の子は「自分の部分木が使う全階層の、いま埋まっている y の最大値」に置く。隣接リストを先に作るので O(ノード数 + エッジ数) で、4,001 ノードで 2.8ms (Jest 実測)。

切り出した副産物として、スクロールバー・エッジ生成・translateExtent の計算・定数も src/features/shared/assembly_tree/ に集まり、views 側と新 feature 側が同じバレルから import する。features → views の依存を作らないための引っ越しでもある。

C. 照合フロー hook と局面の導出

useAssemblyExcelImportFlow({ drawingId }) の骨格は 2.1 で見た。コードで確かめたいのは 3 点。

C-1. ポーリングの options

// useAssemblyExcelImportFlow.ts
const jobStatusQuery = useJobStatusQuery(
  { path: { job_status_id: jobStatusId }, requestTimeoutMs: ASSEMBLY_GRAPH_MATCHING_POLL_REQUEST_TIMEOUT_MS },
  {
    // 終端 (完了 / 再試行しても失敗 / 期限切れ) に着いたら止め、再接続で巻き戻らないようにする
    enabled: (query) => jobStatusId != null && pollingStartedAt != null
      && checkShouldContinuePolling(query.state, pollingStartedAt),
    refetchInterval: JOB_STATUS_POLLING_INTERVAL_MS,      // 3 秒
    refetchIntervalInBackground: true,                     // タブが裏でも続ける
    refetchOnReconnect: false,
    // ETIMEDOUT は query を error にしない。ただし起票から 180 秒を超えたら settle させ、期限切れ局面へ進める
    retry: (failureCount, error) => {
      if (pollingStartedAt != null && Date.now() - pollingStartedAt >= ASSEMBLY_GRAPH_MATCHING_POLLING_TIMEOUT_MS) return false;
      return (isAxiosError(error) && error.code === 'ETIMEDOUT') || failureCount < ASSEMBLY_GRAPH_MATCHING_POLL_RETRY_COUNT;
    },
    retryDelay: JOB_STATUS_POLLING_INTERVAL_MS,
  }
);

retry の意味を言葉にすると、「5xx や 404 は 3 回連続で失敗したら諦める (job_status_unavailable)。10 秒 timeout は時計を進めるための失敗なので回数に数えない。ただし何であれ 180 秒を超えたら止める」。

C-2. 局面の判定木

deriveAssemblyExcelImportOutcome は局面と失敗原因を同じ 1 本の判定木で返す (公開する 2 関数 deriveAssemblyExcelImportPhase / deriveAssemblyExcelImportFailureReason はその包み)。判定の順序が仕様そのものなので、そのまま書き出す。

  1. mutation が pending → uploading
  2. mutation が error → failed (start_matching)
  3. mutation に data がない → idle
  4. job_status が終端 (finished / failed / retrying) なら中身を見る:
    • failed / retrying → failed (job_failed)
    • finished で output.kind が internal_error → failed (job_internal_error)、想定外 → job_output_unknown
    • error_csv → validationFailed
    • result で結果 query が error → failed (result_unavailable)、data 待ち → matching、data あり → matched
  5. 終端でなく、最後の応答時刻が起票から 180 秒以上 → failed (polling_timed_out)
  6. 終端でなく、query が error (retry を使い切った) → failed (job_status_unavailable)
  7. それ以外 → matching

4 が 5 より先にあることが、「180 秒ちょうどに届いた成功応答を捨てない」を保証する。逆に 5 が 6 より先にあることで、「10 秒 timeout で query が error のまま 180 秒を迎えた」ケースが job_status_unavailable ではなく polling_timed_out として New Relic に残る。

C-3. 失敗を New Relic に 1 回だけ送る

// failed 局面になるたびに 1 回だけ New Relic に残す。依存は原因だけにして、他の値の更新では再送しない
useEffectOnUpdate(() => {
  if (failureReason == null) return;
  captureException(new Error(`組図エクセルの照合に失敗しました: ${failureReason}`), {
    kind: NR_EXCEPTION_KIND.ASSEMBLY_GRAPH_MATCHING,
    reason: failureReason,           // NRQL の FACET で分ける
    drawingId,
    ...(jobStatusId != null && { jobStatusId }),
    ...buildFailureDetail(failureReason, { startMatchingError, jobStatus, jobStatusError, resultError }),
  });
}, [failureReason]);

純粋関数に副作用を置かず、hook 側で「原因が決まった瞬間」を useEffectOnUpdate で 1 回だけ拾う。buildFailureDetail は原因ごとに調査の起点になる属性 (HTTP status、最後に見たジョブ状態など) を添える。エラー CSV の保存失敗も同じ kind で reason: 'error_csv_download' として別に送る。
