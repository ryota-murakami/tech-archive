Every so often a bug report arrives that is really a story about arithmetic. Somebody wrote a comment claiming a number, the number was wrong, nothing noticed for years because the systems were small, and then the systems got big. This is one of those.

The symptom is a Turbopack build that dies with a message giving no hint of where to look:

Two or more assets with different content were emitted to the same output path

The cause is six missing characters in a filename. The fix deletes two lines and adds one. Getting there requires understanding what those characters were carrying.

1. Background

1.1 What a bundler is doing when it names a file (skip if you know)

Expand: chunks, output paths, and why naming is hard

Your application is thousands of small source files. The browser does not want thousands of small files, and neither does a serverless function cold-start. So a bundler — webpack, Rollup, esbuild, or in this case Turbopack, the Rust bundler that ships as the default in Next.js — groups modules into a smaller number of larger files called chunks, and writes those chunks to disk.

Each chunk needs a name. That name has three jobs at once, and they pull against each other:

  • Unique. Two chunks with different contents must never land on the same path. If they do, one silently overwrites the other and you ship a broken app — or, if the bundler is careful, the build fails loudly. Turbopack is careful.
  • Deterministic. The same input must produce the same name on every machine, every run. Otherwise caching breaks, and so does any test that compares two builds.
  • Readable. When you are staring at a flamegraph or a network waterfall, app_dashboard_page_3f2a.js tells you something and c7f19b2e.js does not.

Uniqueness wants a long hash. Readability wants a short human-legible path. Almost every bundler resolves this the same way: concatenate them. Take a readable prefix derived from the source path, append a hash suffix that carries whatever the path leaves out, and hope the combination is unique.

That "whatever the path leaves out" is doing a lot of work, and it is where this bug lives.

One more concept you will need. In Turbopack, the thing being named is not a file, it is an ident — a structured identity record for an asset. Two chunks can be built from the same directory of source files and still be genuinely different assets: different subsets of modules, different rendering layers (server vs. client), different tree-shaken slices of the same module. The ident is what distinguishes them, and the filename has to encode enough of the ident that distinct idents get distinct files.

1.2 The three pieces that matter

Three functions, spread across three crates, form the whole story. Read them in this order and the bug becomes obvious.

Piece one: AssetIdent and what it hashes

An ident lives in turbopack/crates/turbopack-core/src/ident.rs and holds eight fields:

pub struct AssetIdent {
    pub path: FileSystemPath,           // where it came from
    pub query: RcStr,                   // ?foo=bar
    pub fragment: RcStr,                // #foo
    pub assets: Vec<(RcStr, ResolvedVc<AssetIdent>)>,  // nested idents
    pub modifiers: Vec<RcStr>,          // "async loader", "client chunks", ...
    pub parts: Vec<ModulePart>,         // tree-shaken slices
    pub layer: Option<Layer>,           // server / client / edge
    pub content_type: Option<RcStr>,    // for data: URLs
}

The method output_name() turns one of these into a filename. Its very first act is a destructuring pattern that is, quietly, the thesis of this entire PR:

let AssetIdent {
    path: _,          // <-- deliberately NOT hashed
    query, fragment, assets, modifiers, parts, layer, content_type,
} = self;
Key concept

The path is not part of the hash. It is rendered directly into the readable prefix. Everything else about the ident goes into the hash. So the hash suffix has exactly one job: to separate idents that share a path and differ only in the other seven fields.

There is a second detail worth noticing. The function tracks a boolean, has_hash, set only if at least one of those seven fields is non-empty:

if has_hash {
    let hash = encode_base38(hasher.finish());
    // 7 base38 chars ~= 36 bits of collision resistance
    let truncated_hash = &hash[..7];
    write!(name, "_{truncated_hash}")?;
}

A plain source module with no query, no modifiers, no layer gets no suffix at all — its path alone is its identity, and paths are already unique. So the population at risk of collision is precisely the set of assets that carry identity beyond their path. In a Next.js build, that population is dominated by one thing: chunks.

Piece two: how a chunk's ident is built

Now look at EcmascriptChunk::ident() in turbopack/crates/turbopack-ecmascript/src/chunk/mod.rs. It has to invent an identity for a chunk, which is not a file and has no natural path of its own. It does two things:

// 1. path = the deepest common ancestor of every chunk item's path
let mut common_path = chunk_items.first().path;
for chunk_item in chunk_items {
    while !chunk_item.path.is_inside_or_equal(common_path) {
        common_path = common_path.parent();   // walk up until it contains everything
    }
}

// 2. assets = one entry per chunk item -- this is what makes the chunk unique
let assets = chunk_items.map(|item| (rcstr!("chunk item"), item.content_ident()));

let mut ident = AssetIdent::from_path(common_path);
ident.assets.extend(assets);

Put the two pieces together and the shape of the problem appears. The path — the part that becomes readable and is not hashed — is a common ancestor directory. The assets list — the part that actually distinguishes one chunk from another — goes entirely into the hash.

The collapse

In a large App Router application, a chunk that draws modules from several routes has a common ancestor of app/. A chunk that also pulls something from lib/ has a common ancestor of the project root. Tens of thousands of chunks therefore share a handful of readable prefixes, and the only thing keeping their output paths apart is the hash suffix.

Piece three: the build's last line of defence

Turbopack does not silently let one asset overwrite another. In crates/next-core/src/emit.rs, when two assets resolve to the same output path, it compares their content. If the content is byte-identical it shrugs and writes once. If not, it writes both versions out under node_root as <content-hash>.js so you can diff them, and raises an error-severity issue:

"Two or more assets with different content were emitted to the same output path"

That is the message users were seeing. It is an honest message. It is also, as we are about to see, an almost perfectly unhelpful one.

2. Intuition

2.1 What the hash suffix is actually for

Here is a real filename from the Turbopack test suite, taken apart. This strip is the diagram we will reuse for the rest of the piece — every filename in this story has these four parts.

Now imagine two chunks in the same build. Both pull modules from under app/, so both have the same common-ancestor path. They contain different modules, so their assets lists differ, so their hashes differ. Good — that is the system working:

Everything to the left of the green segment is identical. The seven green characters are carrying the entire distinction between these two files. If they ever match, the two chunks — different modules, different bytes — get the same output path and the build dies.

So the question that decides whether large builds work is simply: how many distinct values can those seven characters take? The comment in the code said roughly 36 bits. It was wrong.

2.2 Base38, and the digit that was never free

Turbopack encodes hashes in base 38, using the alphabet 0-9 a-z _ -. The alphabet is chosen with some care — a comment in base38.rs notes that ~ and . are deliberately excluded because sequences like ~~ and ... trip common Nginx hardening rules and enterprise WAFs, which then return 403 for your JavaScript.

The encoder is fixed-width. It always emits exactly thirteen characters for a 64-bit hash, most significant digit first:

fn encode_base38_fixed<const N: usize>(mut n: u128) -> String {
    let mut buf = [b'0'; N];
    for i in (0..N).rev() {        // fill from the right...
        buf[i] = BASE38_CHARS[(n % 38) as usize];
        n /= 38;
    }                              // ...so buf[0] is the MOST significant digit
}

Why thirteen? Because you need thirteen base-38 digits to hold every 64-bit value:

valueas bits
38129,065,737,908,494,995,45662.97
26418,446,744,073,709,551,61664.00
3813344,498,040,522,809,827,32868.22

Twelve digits is not enough; thirteen is more than enough. And "more than enough" is the trap. Thirteen base-38 digits can express 68.22 bits of information, but the value only needs 64. There are 4.22 bits of slack, and all of it sits in the leading digit.

Concretely: buf[0] = n / 3812, and since 264 is only about 2.03 × 3812, that leading digit can only ever be 0, 1, or 2. Three values out of a possible thirty-eight.

The arithmetic error

Truncating to the first k characters keeps the high-order digits, which means you pay the slack immediately. The correct formula is not k × log2(38); it is 64 − (13 − k) × log2(38). Every truncation loses those 4.22 bits before it loses anything else.

Applying that to the actual code:

truncationdistinct values real bitscomment claimed
&hash[..7] — the ident hash 6,126,580,47932.51"≈ 36"
&hash[..4] — the head hash 111,65316.77"≈ 21"
hash — after this PR 18,446,744,073,709,551,61664.00—

Six billion looks like a comfortably large number. It is not, and the reason is the oldest trap in applied probability.

2.3 The birthday problem, with real numbers

You are not asking "will this specific chunk collide with that specific one?" You are asking "among the n chunks that share a readable prefix, will any two collide?" The number of pairs grows as n2, so the probability of at least one collision is approximately

P(collision)  ~=  1 - exp( -n^2 / 2M )        where M = 6,126,580,479

Pictured with buckets — each bucket is one possible hash value, each pip is a chunk. With few chunks and many buckets, life is fine:

The buckets in the second row are not fuller because the hash is worse — the hash is the same. There are simply more chunks. The failure mode is a property of application size, and nothing else.

Those bottom rows are not hypothetical. The PR cites two reports:

  • #97765 — a deterministic reproduction with roughly 120,000 chunks sharing one prefix. It fails byte-identically on every run: same collided path, same rejected content hashes, build after build.
  • #96976 — a production App Router application emitting about 69,000 server chunks, with a measured failure rate near 9% per build. (9%, not 32%, because not every one of those 69,000 shares the same ancestor prefix — the birthday count applies within each prefix group, and the groups are smaller than the total.)

And after the fix, with all 64 bits retained? At 120,000 chunks the probability of a collision is about 4 × 10−10. You would need roughly 10 million chunks sharing a prefix before reaching a 0.0003% chance. The failure mode is gone, not reduced.

2.4 Why it always looked like your branch's fault

The arithmetic is the bug, but the ergonomics are what made it expensive. Two properties combine badly.

The hash is deterministic, so the build is not flaky — it is stuck. Given a fixed module graph, the collision either exists or it does not, and it reproduces exactly. That sounds like good news for debugging. It is not, because of the second property:

Which pair collides is chosen by the hash, not by anything structural. The two chunks that collide have nothing to do with each other. They are not in the same route, they do not import each other, they are not even necessarily near each other in the tree. They are simply the pair whose 64-bit hashes happened to agree in their top 32.5 bits.

The consequences follow mechanically, and every one of them points at an innocent party:

  • Any commit that changes the module graph — adding a route, importing a library, splitting a component — reshuffles which chunks exist, and so reshuffles which pair collides. The failure therefore lands on whichever branch last touched the graph, and looks like that branch's fault.
  • git bisect works perfectly and tells you nothing useful. It converges on a real commit — the one that pushed the population over the edge — but that commit is innocent, and no file in its diff is responsible.
  • Moving a module to "fix" it does fix it, which is the cruelest part, because it teaches you the wrong lesson. You have not removed the collision; you have relocated it.
  • The PR notes a particularly clean demonstration: renaming a module inside a colliding chunk does not change the chunk's name at all. Same two chunks, same seven-character name, and the renamed file now visibly listed inside one of them. Nothing you can see in the error has any causal relationship to the error.
Worth internalising

A deterministic failure whose location is chosen by a hash function is harder to debug than a flaky one. Flakiness at least advertises that the cause is not where you are looking. This failure impersonates a normal, reproducible, bisectable regression right up until you try to fix it.

3. The Code

The pull request touches 711 files. Exactly two of them contain a decision; one of those two is an accident. Everything else is regenerated output. It is worth walking the change in that order, because the ratio is itself informative about what kind of change this is.

3.1 The change itself

All of it, in turbopack/crates/turbopack-core/src/ident.rs:

         if has_hash {
             let hash = encode_base38(hasher.finish());
-            // 7 base38 chars ~= 36 bits of collision resistance
-            let truncated_hash = &hash[..7];
-            write!(name, "_{truncated_hash}")?;
+            // Use the complete fixed-width base38 encoding of the 64-bit hash.
+            //
+            // This suffix is what distinguishes idents that share a readable
+            // name prefix, so truncating it makes distinct output paths collide
+            // for large module graphs, failing the build with "Two or more
+            // assets with different content were emitted to the same output
+            // path". Keeping all 64 bits removes that failure mode, at the cost
+            // of a slightly longer file name.
+            write!(name, "_{hash}")?;
         }

Two lines deleted, one added, and six lines of comment explaining why the truncation was never safe — which is the part that stops someone reintroducing it in two years to shorten filenames.

Note what the change does not do. It does not change the hash function, the hashed inputs, the alphabet, or the encoding. encode_base38 was already returning the full thirteen characters; the old code was throwing six of them away one line later. The fix is to stop discarding information that had already been computed.

Design note

The PR author explicitly offers the alternative in the description: "If you would rather solve this by hashing more distinguishing input rather than widening the truncation, I am glad to rework it; the length is the smallest change that removes the failure mode." That is the right instinct. Feeding more input into the hash — say, the full chunk-item paths rather than the common ancestor — would produce prettier names, but it changes what identity means, with consequences for caching and incremental rebuilds. Keeping the bits you already have is strictly smaller.

3.2 The other 709 files

Turbopack's snapshot tests pin emitted chunk names, and the chunk contents themselves embed the names of other chunks — a runtime entry file literally lists the URLs it must fetch. So changing the naming scheme rewrites the whole fixture corpus. Those 709 files are all regenerated output, and they divide into two kinds, which is where the walkthrough gets interesting.

Most files look exactly like you would predict. The seven old characters are a prefix of the thirteen new ones, because it is the same hash of the same input:

Kind two: the hash changed entirely

But some files do not follow the pattern at all. In the same test directory, the entry chunk went from _0qno3y- to _1ilscbcayntrz, and 0qno3y- is emphatically not a prefix of 1ilscbcayntrz. Elsewhere, _210e6bp became _0clmgi5qq_o2b. The hash input changed, not just its width. Why?

Because of one method in turbopack/crates/turbopack-browser/src/ecmascript/evaluate/chunk.rs:

async fn ident_for_path(&self) -> Result<Vc<AssetIdent>> {
    let mut ident = self.ident.owned().await?
        .with_modifier(rcstr!("ecmascript browser evaluate chunk"));

    ident.modifiers.extend(evaluatable_assets.iter()
        .map(|entry| entry.ident().to_string().owned()).try_join().await?);

    ident.modifiers.extend(self.other_chunks.await?.iter()
        .map(|chunk| chunk.path().to_string().owned())   // <-- OUTPUT paths
        .try_join().await?);

    Ok(ident.into_vc())
}

An evaluate chunk is the bootstrap file: it must know the URLs of every other chunk in its group, so it can fetch them. Those output paths are folded into its own ident as modifiers — and modifiers are hashed. So when the sibling chunks' names got six characters longer, the evaluate chunk's hash input changed, and its own name changed wholesale.

3.3 Where the names got shorter

The PR summarises the cost as "6 extra characters per emitted chunk filename". That is true for short names, and the reader's next question is the obvious one: on a deeply nested monorepo path, does the filename now blow past what the filesystem will take?

It does not, and the reason is a length cap that was already in output_name, immediately after the hash suffix is appended:

// Everything before i is hashed away; everything after i is kept readable.
let mut i = 0;
static NODE_MODULES: &str = "_node_modules_";
if let Some(j) = name.rfind(NODE_MODULES) { i = j + NODE_MODULES.len(); }

const MAX_FILENAME: usize = 80;
if name.len() - i > MAX_FILENAME {
    i = name.len() - MAX_FILENAME;
    if let Some(j) = name[i..].find('_') && j < 20 { i += j + 1; }  // snap to a separator
}
if i > 0 {
    let hash = encode_base38(hash_xxh3_hash64(&name.as_bytes()[..i]));
    let truncated_hash = &hash[..4];               // the purple head hash
    name = format!("{}_{}", truncated_hash, &name[i..]);
}

The readable tail is capped at 80 characters. Anything longer gets cut, the cut point snaps forward to the next _ (if one is within 20 characters, so segments are not sliced mid-word), and the discarded head is replaced by a four-character hash of itself. This is where the purple segment in every diagram comes from.

Now watch what happens to a name that was already near the cap. Six more characters push it over, the split point moves right, snaps past the next separator, and an entire path segment — turbopack-tests_ — disappears into the head hash:

Real names from the regenerated snapshots. The file got ten characters shorter because a sixteen-character path segment was traded for a four-character hash.

The real cost

The cost of this PR is not filename length — the 80-character cap bounds that regardless, so total length stays around 90 either way. The cost is readability at the front: names already near the cap surrender one more path segment to the head hash. That is a fair trade for a build that completes, but it is the honest accounting, and it is not the accounting in the PR description.

3.4 The truncation that was left alone

You will have noticed that the head hash is also truncated, to four characters, with a comment making the same optimistic claim: "4 base38 chars ≈ 21 bits". By the corrected formula it is 16.77 bits — only 111,653 distinct values. Five hundred colliding names would be a coin flip. The PR does not touch it. Is that an oversight?

No, and understanding why is the best test of whether the mechanism has landed. The two truncations face wildly different populations.

ident hash (was 7)head hash (still 4)
separates every chunk sharing a common-ancestor path only names whose last 80 characters are byte-identical but whose heads differ
population tens of thousands, growing with app size a handful; two paths must agree on 80 trailing characters to even compete
backed up by nothing — it was the sole discriminator the full 13-character ident hash, which lives in the tail and always survives the cut

That last row is the load-bearing one. The ident hash is appended before the length cap runs, and the cap preserves the final 80 characters — comfortably more than 13. So the full 64-bit ident hash is always inside the kept tail. The head hash never has to distinguish two assets on its own; it only breaks ties between differing prefixes of names that are otherwise identical. The one case where it stands alone is an ident with no hash suffix (a plain module, has_hash == false); there the head hash is the sole discriminator, which is a real if small exposure — and one this PR neither creates nor worsens.

The general lesson

Truncating a hash is safe exactly in proportion to how small the population it must separate is, and how much other distinguishing information survives alongside it. The seven-character ident hash violated both conditions: unbounded population, no backup. The four-character head hash satisfies both. Same arithmetic error in the comment; only one of them is a bug.

3.5 Loose ends

Two things a reader diffing this PR will trip over, neither of them substantive:

  • Cargo.lock, +1 line. It adds rustc-hash 2.1.1 to the dependency list of turbo-tasks-fetch — a rebase artifact, unrelated to naming.
  • Two failing checks. test/production/deterministic-build/deployment-id.test.ts fails under turbopack production (3/7) (job log), and thank you, next fails — that one is the PR-description linter, which is expected on a re-pushed PR. The author's own comment explains the branch name: "I needed to recreate the PR, because something about commit signing requirements..." The production-test failure is real and visible in CI; determining its cause requires running it, which is beyond what the diff shows.

One risk the PR flags and then dismisses: every emitted filename changes on upgrade. Its stated reasoning is that nothing reads these names across versions — they are internal build output, referenced only by manifests generated in the same build. That is the author's claim rather than something visible in the diff, though it matches how the names are used everywhere they appear here.

Closing

The thing to carry away is not "hashes should be longer". It is that a truncated hash is a bet on a population size, and the bet is usually made once, in a comment, by someone who is not thinking about what the field will look like in five years. Here the bet was an application will not have a hundred thousand chunks under one directory, and it held until it did not.

What made the failure expensive was not the arithmetic but the shape of the blame. A collision chosen by a hash function has no relationship to anything a human can see in the error, and every debugging instinct — bisect, revert, move the file — produces a result that looks like progress and teaches the wrong lesson. That is the part worth recognising next time: when a fix "works" but you cannot say why the failing pair was that pair, you have probably relocated a collision rather than removed one.

The remedy, in the end, was to stop throwing away six characters that had already been computed.
