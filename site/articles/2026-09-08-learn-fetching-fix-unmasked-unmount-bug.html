'fetching' を消したら別のバグが出た理由

結論を先に書きます。新しいバグを作ったのではありません。 もう一つ別のバグが最初からあり、間違った数え方がそれを隠していました。 数え方を直したので、隠れていた方が表に出ました。

背景

FileDownloadBox の構造を知っている人は「狭い背景」へ。

深い背景：ダウンロードボックスとは何か

CSV や xlsx のエクスポートは、BE でジョブを回してから署名付き URL を受け取り、ブラウザで保存します。 この一連を UI で見せるのが右下のダウンロードボックスです。 複数ファイルを順番に処理するキューで、各ファイルは downloadStatus を持ちます。

ボックスの × ボタンにはガードがあります。 まだ処理が終わっていないファイルがある間は閉じられません。 閉じるとキューが空にされるので、進行中のファイルが黙って消えるのを防ぐためです。

ガードの判定材料が remainingFileCount（残り件数）です。 これは「まだ終わっていない状態のファイルの数」で、0 のときだけ × が有効になります。

狭い背景：二つの層に分かれている

キューのデータを持つコンポーネントと、キューを処理するループを持つコンポーネントが別です。 この分離が今回の話の前提です。

FileDownloadBoxProvider · src/pages/_app.tsx:220
fileDownloadRequests（キュー本体）と remainingFileCount を持つ。 _app.tsx 直下なので、ページ遷移しても消えない。
FileDownloadBox · src/components/layouts/layout/Layout.tsx:88
1 秒ごとに次の idle を探して処理する待ち受けループを持つ。 Layout の中にあるので、Layout が外れると一緒に unmount される。

Next.js Pages Router では、各ページが getLayout を持ち、_app.tsx が Component.getLayout ?? ((page) => page) で適用します。 同じ Layout を返すページ同士の遷移では React が Layout を再利用します。 一方、getLayout を持たないページに遷移すると Layout そのものが外れます。

出典: Next.js · Pages and Layouts · Per-Page Layouts ／ src/pages/_app.tsx:162

要点

バグは二つあります。別々のものです。

バグ A（数え方）バグ B（unmount で取り残し）
何が起きる remainingFileCount が 'fetching' を数え、'downloading' を数えない Layout が外れてループが止まると、'downloading' のファイルが誰にも終了させられず残る
いつからある #1595 以降 Provider と Box が別層になった時点から
直したコミット 90e940f42（9/5） f9ce29f45（9/8、案1）

具体的なデータで見ます。キューに 1 件、状態は downloading。 ループはすでに止まっていて、この 1 件を completed にも error にもする者はいません。 この状態はバグ B が作ります。 

fileDownloadRequests = [
  { fileType: 'clients_bulk_update', downloadStatus: 'downloading', fileName: '...' }
]

バグ A あり（修正前）

数える対象: ['idle', 'fetching']

remainingFileCount = 0

downloading は数えない。× が有効。ユーザーは閉じられる。
バグ B は起きているが、症状が出ない。

バグ A 修正後

数える対象: ['idle', 'downloading']

remainingFileCount = 1

downloading を数える。× が無効。誰も終わらせないので、リロードまで閉じられない。
バグ B の症状が出る。

要点 バグ A の「実行中を数えない」という誤りが、バグ B の「実行中が取り残される」という誤りを打ち消していました。 A だけ直すと、B の取り残しが正しく「残り 1」と数えられ、ガードが働き続けます。 A の修正は正しい。B も直す必要があった。それだけです。

仕組み

1. 状態は 4 つだけ

export type DownloadStatus = 'idle' | 'downloading' | 'completed' | 'error';

出典: src/components/layouts/file_download_box/FileDownloadBoxProvider.tsx:16

idle downloading completed error fetching — 型に無い。代入箇所も無い

遷移は次の通りです。idle だけがループの入口で、completed と error が出口です。

idleループが拾う downloading保存成功 completed
downloadingAPI 失敗 / ポーリング上限 / unmount（案1で追加） error

2. 残り件数の定義と、修正前後の値（計測）

現行コード:

const remainingFileCount = useMemo(
  () =>
    fileDownloadRequests.filter((file) =>
      ['idle', 'downloading'].some((status) => status === file.downloadStatus)
    ).length,
  [fileDownloadRequests]
);

出典: FileDownloadBoxProvider.tsx:148-154

修正コミット 90e940f42 の差分は 1 行です。 

-        ['idle', 'fetching'].some((status) => status === file.downloadStatus)
+        ['idle', 'downloading'].some((status) => status === file.downloadStatus)

出典: git show 90e940f42 -- FileDownloadBoxProvider.tsx

同じ filter を Node で実行した結果です。推測ではなく、この説明を書く前に実際に走らせました。

キューの中身旧: idle + fetching新: idle + downloading
idle ×111
downloading ×101
completed ×100
error ×100
idle ×1 + downloading ×112

赤い行が全てです。downloading 1 件が、旧では 0、新では 1。 そして error はどちらでも 0 です。案1 が error を選んだ理由はこの最後の点です。

3. ループは idle しか拾わない

const fileIndex = fileDownloadRequestRef.current.findIndex(
  (file) => file.downloadStatus === 'idle'
);

出典: FileDownloadBox.tsx:221-223

すでに downloading になった行は、この findIndex に二度と引っかかりません。 その行を completed / error へ進めるのは、それを downloading にした同じループの同じ周回だけです。 ループが途中で止まれば、その行は永久に downloading です。

4. Layout が外れるとループが止まる

案1 より前の cleanup は次の 1 行でした。 

return () => {
  unmountRef.current = true;
};

React はコンポーネントが DOM から外れるとき、effect の cleanup を最後に一度呼びます。 ループは if (unmountRef.current) break; で次の周回に抜けますが、進行中の行の状態は触りません。

出典: React · useEffect —「After your component is removed from the DOM, React will run your cleanup function.」 ／ FileDownloadBox.tsx:218

5. どの操作で Layout が外れるか

案件詳細の「戻る」は router.push('/orders') です。 src/pages/orders/index.tsx は getLayout を持たず、 マウント直後に /orders/table か /orders/kanban へ router.push するだけのページです。 つまり一瞬だけ Layout 無しの状態を通ります。

出典: src/views/orders/detail/components/OrderDetailPageHeader.tsx:52 ／ src/pages/orders/index.tsx:30-42（getLayout の定義なし、grep で 0 件）

1. ダウンロード開始
ループが idle → downloading にする。
残り 1。× は無効。（旧コードでは残り 0、× が有効）
2. 案件詳細を開く
同じ Layout チェーンなので Box はそのまま。ループも生きている。
3. 「戻る」→ /orders
getLayout 無し → Layout が外れる → Box が unmount → ループが break。
キューの行は downloading のまま。Provider は _app にいるので消えない。
4. /orders → /orders/table にリダイレクト
Layout が再びマウント。新しい Box、新しいループ。
5. 新しいループは idle だけ探す
取り残された downloading は無視される。
新コード: 残り 1 → handleCloseClick が early return、× は pointerEvents: 'none'。リロードまで閉じられない。
旧コード: 残り 0 → × が押せる。閉じればキューが空になり、症状は見えない。

出典: PR #4294 · o-bata の再現手順 ／ ガード: FileDownloadBox.tsx:435, :493

未検証 この説明を書いたセッションでは、ブラウザで「ダウンロード中 → 案件詳細 → 戻る」を再実行していません。 遷移経路と各行の挙動はコードから確認しました。× が押せなくなる症状そのものはレビューコメントの報告に依っています。

6. 案1 が何をするか

return () => {
  unmountRef.current = true;

  // 待ち受けループが止まるので、downloading のまま残すと閉じられなくなる
  setFileDownloadRequests((previous) => {
    const next = [...previous];
    for (const fileDownloadRequest of next) {
      if (fileDownloadRequest.downloadStatus === 'downloading') {
        fileDownloadRequest.downloadStatus = 'error';
      }
    }
    return next;
  });
};

出典: FileDownloadBox.tsx:417-430（f9ce29f45）

unmount の瞬間に、進行中の行を error に倒します。 setFileDownloadRequests は Provider の state を更新する関数で、Provider は生きているので届きます。 error は残り件数に入らない（上の表）ので、再マウント後の × は有効になります。

誤解しやすい点 「'fetching' を消したから壊れた」ではありません。 'fetching' 行は、実行中を数え漏らすバグでした。 その数え漏らしが、取り残しバグを結果的に隠していただけです。 戻せば取り残しは再び見えなくなりますが、進行中に閉じられる元のバグも戻ります。
一般化すると 「まだ終わっていない」と数える状態には、ワーカーが止まるすべての経路で出口（completed / error）へ運ぶ処理が必要です。 API 失敗とポーリング上限には出口がありましたが、unmount にはありませんでした。 数え方だけ正しくして出口を足さないと、ガードが固まります。

このコードベースでは

  • DownloadStatus は 4 値（FileDownloadBoxProvider.tsx:16）。 'fetching' を再導入しない。Serena メモ pattern_download_status_no_fetching にも記録あり。
  • 残り件数は idle と downloading（同 :148-154）。コメント「ダウンロード待ちか、ダウンロード中」と一致している。
  • × ガードは 2 箇所。ハンドラの early return（FileDownloadBox.tsx:435）と、アイコンの pointerEvents: 'none'（同 :493）。
  • ループの入口は idle のみ（同 :221-223）。unmount 時の出口は案1 の cleanup（同 :417-430）。
  • Provider は _app.tsx:220、Box は Layout.tsx:88-90。層が違うので、Box が unmount しても Provider の state は残る。この前提を崩す変更（Box を _app へ移す案2）は取り消し済み。理由は Serena メモ pattern_file_download_box_host_outside_layout。
  • getLayout を持たないページは src/pages/orders/index.tsx（リダイレクト専用）。ここを通る動線が、Layout を一度外す。
