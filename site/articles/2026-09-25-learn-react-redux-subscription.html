React Redux の Subscription とは何か

Redux のストアは「何かが変わった」としか言わない、ぶっきらぼうなイベント発行器です。Subscription は、その素っ気ない通知をコンポーネントツリーの親から子へ、順番を守って配り直すための小さな中継網です。このページでは、なぜそんな中継が必要なのか、どう動くのか、そしてどこまで守ってくれるのかを、実際のソースと実測ログで確かめていきます。

1. Background

Redux の store.subscribe を知っている人は、次の「狭い背景」まで飛ばして構いません。

広い背景：Redux ストアはただのイベント発行器

Redux のストアが公開しているのは、実質的に 3 つの関数です。getState() は現在の状態を返し、dispatch(action) は reducer を通して状態を更新し、subscribe(listener) は「dispatch されたら呼んでほしい関数」を登録します。Mark Erikson が React-Redux の歴史を解説した記事で示している最小実装は、驚くほど短いものです。

function createStore(reducer) {
  let state
  const listeners = []
  return {
    getState: () => state,
    subscribe(l) { listeners.push(l); return () => listeners.splice(listeners.indexOf(l), 1) },
    dispatch(action) {
      state = reducer(state, action)
      listeners.forEach(l => l())   // 状態が変わったかどうかは確認しない。引数も渡さない
    },
  }
}

ここで注目すべき性質は二つあります。第一に、ストアは何が変わったかを教えてくれません。リスナーは毎回自分で getState() を呼び、自分に関係する部分を取り出し、前回と比べる必要があります。第二に、リスナーは登録された順に呼ばれます。この「登録順」という何気ない性質が、React と組み合わせたときに厄介な問題を引き起こします。

狭い背景：React は子のエフェクトを先に実行する

React はコミット時、エフェクト（useEffect / useLayoutEffect）を子から親の順で実行します。ですから、各コンポーネントがマウント時のエフェクトの中で素朴に store.subscribe を呼ぶと、子のほうが親より先にストアへ登録されてしまいます。すると dispatch のたびに、子のリスナーが親より先に走ることになります。

これが問題になるのは、子が「親から渡された props」を使ってストアから値を取り出す場合です。親が次のレンダーで渡すはずの新しい props を、子はまだ受け取っていません。その状態で子が古い props を使ってストアを読むと、次の二つの不具合が起こります。

用語：stale props と zombie children stale props — 親が新しい props を渡して再レンダーするはずなのに、その前に子のセレクタが古い props で実行されてしまう状況です。
zombie child — 子が親より先に購読していて、ある action がその子のデータ（たとえば todo の 1 件）を削除したとします。親は次のレンダーでその子を描かなくなるはずですが、子のリスナーが先に走り、もう存在しないデータを読んで例外を投げます。
出典: react-redux.js.org / Hooks / Usage Warnings

公式ドキュメントによれば、v4 まではこの種のバグ報告が繰り返し寄せられていました。v5 からは ownProps との整合性を保証しようとしており、v7 以降その保証を担っているのが、ここで扱う Subscription です。

2. Intuition

考え方そのものは単純です。ストアに直接つながるのは根っこの 1 本だけにし、そこから先は「最寄りの connect された祖先」経由で通知を受け取ることにします。通知はツリーの形に沿って流れ、各中継点は自分の処理（再レンダー）が終わってから、下流に「どうぞ」と伝えます。

図 A — Subscription のツリー。矢印ではなく入れ子で「誰の addNestedSub に登録されているか」を表しています

  • Redux store listeners = [root.handleChangeWrapper]
    • <Provider> の Subscription onStateChange = notifyNestedSubs
      • connect(TodoList) の Subscription onStateChange = checkForUpdates
        • useSelector in <TodoItem id="a"> addNestedSub(listener)
        • useSelector in <TodoItem id="b"> addNestedSub(listener)
      • useSelector in <Header> Provider の addNestedSub に直結
ストア Provider の root Subscription connect が作る中継 Subscription useSelector（葉。自分の Subscription は作らない）

具体例で考えてみましょう。state が { ids: ['a','b'], byId: { a: {...}, b: {...} } } で、removeTodo('a') が dispatch されたとします。

  1. ストアは唯一のリスナーである Provider の root を呼びます。
  2. root は子リスト（connect(TodoList) と <Header> の useSelector）へ通知します。
  3. connect(TodoList) は mapState を再計算し、ids が ['b'] に変わったことに気づきます。ここで子へ通知せずに止まり、自分の再レンダーを予約します。
  4. React が TodoList を再レンダーし、TodoItem id="a" はツリーから消えます。
  5. コミット後、connect(TodoList) はようやく notifyNestedSubs() を呼び、残った子へ通知を流します。

要するに Subscription は、「ストアの登録順」を「コンポーネントツリーの深さ順」に置き換えるための仕組みです。下のシミュレータで、中継点が止まる様子を確かめてみてください。

3. Mechanics

直感が掴めたところで、実装を読んでいきます。src/utils/Subscription.ts は 184 行で、二重連結リストによるリスナー集合と、それを包む参照カウント付きの購読オブジェクトの二層でできています。

3.1 公開インターフェース

export interface Subscription {
  addNestedSub: (listener: VoidFunc) => VoidFunc   // 子（または useSelector）が自分を登録する入口。解除関数を返す
  notifyNestedSubs: VoidFunc                        // 登録された子へ順に通知する
  handleChangeWrapper: VoidFunc                     // 親（またはストア）に渡す自分のリスナー。onStateChange を呼ぶだけ
  isSubscribed: () => boolean                       // 「自分自身」が購読中か（子がいるだけでは false）
  onStateChange?: VoidFunc | null                   // 通知を受けたときの振る舞い。外から差し込む
  trySubscribe: VoidFunc                            // 自分自身として購読を開始（冪等）
  tryUnsubscribe: VoidFunc                          // 自分自身として購読を終了（冪等）
  getListeners: () => ListenerCollection            // テスト・デバッグ用
}

src/utils/Subscription.ts:81-90

設計上の要点は、onStateChange が外から差し込まれることです。Subscription 自身は「通知が来たら何をすべきか」を知りません。Provider は notifyNestedSubs をそのまま差し込み（素通しの中継）、connect は checkForUpdates を差し込みます（再計算してから、必要なら止める）。

3.2 親への接続：trySubscribe

function trySubscribe() {
  subscriptionsAmount++
  if (!unsubscribe) {
    unsubscribe = parentSub
      ? parentSub.addNestedSub(handleChangeWrapper)   // 親 Subscription があれば親へ
      : store.subscribe(handleChangeWrapper)          // なければストアへ直接
    listeners = createListenerCollection()
  }
}

src/utils/Subscription.ts:137-146

createSubscription(store, parentSub?) の第 2 引数の有無だけで、「ストア直結の root」になるか「誰かの子」になるかが決まります。そして parentSub.addNestedSub は内部で親自身の trySubscribe() を呼ぶので、子が先に購読を始めても、祖先を芋づる式に接続していきます。

実測 1：子が先に購読しても、ストアへの登録は 1 回だけ 実際の Subscription.ts を /tmp にコピーし（import 拡張子のみ修正）、Node 24 で次の順に呼びました：parent.trySubscribe() → root.trySubscribe() → 子 2 つ。 
parent.trySubscribe()
  [store] subscribe (total=1)      ← 子の購読が root を連鎖的に接続
root.trySubscribe()                ← 既に接続済みなので store には何も起きない
子を 3 つ作ってから root を購読する別ケースでも、[store] subscribe は 1 回だけでした。これは React の「子エフェクトが先」という順序と噛み合っています。Provider の useLayoutEffect が走る前に子が接続を始めても、壊れません。

3.3 子への配信：リスナー集合と notify

リスナー集合は配列ではなく、first / last を持つ二重連結リストです。購読解除は O(1) で済み、notify はリストを先頭から辿ります。

notify() {
  batch(() => {
    let listener = first
    while (listener) {
      listener.callback()
      listener = listener.next      // callback の後で next を読む
    }
  })
},

src/utils/Subscription.ts:25-33

注意：batch は v9 では何もしない batch の実体は defaultNoopBatch で、コールバックをそのまま呼ぶだけです（src/utils/batch.ts:2-4）。React 18 以降の自動バッチングに任せているため、ここで unstable_batchedUpdates のようなラップは行われません。
実測 2：通知は深さ優先で流れる root → parent → (childA, childB) で、childA の下に useSelector 相当の葉を 1 つ付けて dispatch しました。 
root.onStateChange -> notifyNestedSubs
  parent.onStateChange
    childA.onStateChange
      leaf (useSelector listener)   ← childB より先
    childB.onStateChange
各 onStateChange が同期的に notifyNestedSubs() を呼べば、通知は深さ優先・登録順で流れます。兄弟間の順序は、addNestedSub された順です（test/utils/Subscription.spec.ts の listeners are notified in order も同じことを検証しています）。

3.4 参照カウント：「自分」と「子のため」を区別する

ある Subscription が親につながっている理由は二つあり得ます。自分自身が通知を欲しいか、子が自分を経由して通知を欲しいかです。subscriptionsAmount はこの二種類をまとめて数え、0 になったときだけ親から外れます。一方 selfSubscribed は「自分自身」の分だけを表すフラグで、trySubscribe / tryUnsubscribe を何度呼んでも二重に数えないようにしています。

childA.isSubscribed() true
childA self-unsubscribed; isSubscribed() false listeners 1   ← 葉がまだ 1 つ残っている
leaf removed; childA listeners 0                            ← ここで初めて親から外れる

isSubscribed() は「自分自身が購読中か」だけを返し、子の有無は反映しません（src/utils/Subscription.ts:133-135）。

3.5 connect の中継ロジック：いつ止め、いつ流すか

中継点が「親の再レンダーが終わるまで子に言わない」を実現している場所は、connect.tsx の二つの関数です。

// 通知を受けたとき（subscribeUpdates 内の checkForUpdates）
newChildProps = childPropsSelector(store.getState(), lastWrapperProps.current)
if (newChildProps === lastChildProps.current) {
  if (!renderIsScheduled.current) notifyNestedSubs()   // 自分は変わらない → すぐ子へ流す
} else {
  lastChildProps.current = newChildProps
  childPropsFromStoreUpdate.current = newChildProps
  renderIsScheduled.current = true                       // 自分は変わる → 子へは流さず、再レンダーを予約
  additionalSubscribeListener()                         // useSyncExternalStore のリスナーを叩く
}

src/components/connect.tsx:120-172（抜粋）

// 再レンダーのコミット後（useLayoutEffect で呼ばれる captureWrapperProps）
lastWrapperProps.current = wrapperProps
renderIsScheduled.current = false
if (childPropsFromStoreUpdate.current) {
  childPropsFromStoreUpdate.current = null
  notifyNestedSubs()                                    // ここで初めて子へ流す
}

src/components/connect.tsx:84-93, 900-907

connect はさらに、自分の Subscription を新しい Context 値として子孫へ提供します（connect.tsx:808-822 の overriddenContextValue）。子孫の connect や useSelector が useContext で受け取る subscription は、Provider のものではなく、この最寄りの connect のものになります。ツリーの入れ子は、こうして Context の上書きによって作られています。

useSelector は「葉」であって「中継点」ではない useSelector は useSyncExternalStoreWithSelector(subscription.addNestedSub, store.getState, ...) と書かれており、Context から受け取った Subscription の addNestedSub を subscribe 関数として渡すだけです（src/hooks/useSelector.ts:243-249）。自分の Subscription は作らず、Context Provider を描画することもできません。そのため、フックだけで組んだツリーでは、すべての useSelector が Provider の root にフラットにぶら下がります。

ドキュメントと実測の食い違い：「順序」は守られるが、「ゾンビの 1 回」は消えない 図 C で connect は約束どおり、自分の mapState → 再レンダー → コミット → 子へ通知という順序を守りました。ところが子のセレクタは、ステップ 6 で一度だけ、削除済みのデータに対して実行されています。原因は購読解除のタイミングです。useSelector の購読は useSyncExternalStore 経由なので、解除は passive エフェクトの cleanup（ステップ 7）で行われます。一方、connect が子へ通知するのは layout エフェクト（ステップ 5）です。この二つの間に、アンマウント予定の子のリスナーがまだリストに残っています。

この例外がテストを落とさなかったのは、useSyncExternalStoreWithSelector がストア更新経由のセレクタ例外を握りつぶし、再レンダーへ回すからです。リポジトリ自身のテスト allows dealing with stale props by putting a specific connected component above the hooks component（test/hooks/useSelector.spec.tsx:594-640）も、最後に expect(sawInconsistentState).toBe(true) と書いています。つまり「不整合な状態は観測されうるが、アプリは壊れない」ことを期待値にしているわけです。
未検証：例外を握りつぶす正確な場所 例外が use-sync-external-store/with-selector の checkIfSnapshotChanged 付近で catch されている、というのは React の実装から推測したもので、今回は該当コードを読んでいません。確かめるには、node_modules/use-sync-external-store の shim 実装と、React 19 本体の useSyncExternalStore 実装を読む必要があります。

4. In this codebase

このリポジトリで createSubscription を呼んでいるのは、Provider と connect の 2 か所だけです。useSelector は Context 経由でそれを受け取って使うだけです。

Provider：ツリーの根を作る

const contextValue = React.useMemo(() => {
  const subscription = createSubscription(store)          // parent なし = ストア直結の root
  return { store, subscription, getServerState: ... }
}, [store, serverState])

useIsomorphicLayoutEffect(() => {
  subscription.onStateChange = subscription.notifyNestedSubs   // 素通しの中継
  subscription.trySubscribe()
  if (previousState !== store.getState()) {
    subscription.notifyNestedSubs()                       // 描画中に state が進んでいたら追いつかせる
  }
  return () => { subscription.tryUnsubscribe(); subscription.onStateChange = undefined }
}, [contextValue, previousState])

src/components/Provider.tsx:62-98（抜粋）

previousState との比較は、初回レンダーからエフェクト実行までの間に dispatch されたケースへの対策です。そのあいだ root はまだストアに登録されていないので、取りこぼした更新をここで配り直しています。

connect：中継点を作り、Context を上書きする

const subscription = createSubscription(
  store,
  didStoreComeFromProps ? undefined : contextValue!.subscription,
)

src/components/connect.tsx:791-794

<Connected store={otherStore} /> のように props でストアを渡された場合は、親を持たない独立した root になります。このとき Context は上書きしません（connect.tsx:809-814）。「props 由来のストアを購読する connect が、Context 由来のツリーに割り込まない」ためのルールです。また mapStateToProps を持たない connect（shouldHandleStateChanges === false）は Subscription を作らないので、ツリー上では透明になります。
