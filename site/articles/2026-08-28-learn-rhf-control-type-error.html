control の Type エラーの原理

赤い波線は、入力欄の型が間違っているからではありません。
control という一つの箱に、入力の形と送信の形が両方刻印されていて、受け取る側がその片方しか知らない、という話です。

1背景 — フォームライブラリが型を三つ持つ理由

画面上の入力欄が扱う値と、サーバへ送る値は、同じである必要がありません。日付を "2026-08-28" と打って、検証が通ったあと Date にして送る。取引先名は camelCase のまま編集して、送信の直前に snake_case のリクエストボディへ詰め替える。こうした「入力の形」と「出力の形」の分裂は、Zod の transform や coerce では日常茶飯事です。

React Hook Form（以下 RHF）は、長らくこの分裂を型の上で無視していました。フォームの型は一つ、TFieldValues だけ。検証を通ったあとに形が変わっても、handleSubmit のコールバックは入力と同じ型を受け取るとされていた。

公式ドキュメントは、今ではこの分裂を第三 generic として正面から扱います。useForm の第 1 引数が入力、第 3 引数が resolver の出力です。

// https://react-hook-form.com/docs/useform/handlesubmit
// 「Resolver with Transformed Values」
const { register, handleSubmit } = useForm<FormInput, unknown, FormOutput>({
  resolver: zodResolver(schema),
})

const onSubmit: SubmitHandler<FormOutput> = (data) => {
  // data は変換後。emailOrPhone ではなく isEmail / isPhone / value
}

出典: react-hook-form.com/docs/useform/handlesubmit ／ 同じ型の分け方は @hookform/resolvers の Zod 解説 でも z.input / z.output として推奨されている

@hookform/resolvers はさらに強く言います。入力と出力が違うスキーマに対して useForm<FormData> と一つだけ書くのは誤りで、三つ書くのが正しい、と。

// ❌ 単一 generic は入力と出力を同じ型に固定してしまう
useForm<FormData>({ resolver: zodResolver(schema) })

// ✅ 入力・文脈・出力を分ける
useForm<z.input<typeof schema>, unknown, z.output<typeof schema>>({
  resolver: zodResolver(schema),
})

出典: resolvers TYPES_AND_INTERFACES.md 「Fixing Type Mismatch with Generics」

ここで言う control とは

useForm が返すオブジェクトのうち、フィールドを登録したり監視したりするための操舵輪です。入力コンポーネントへ props で渡し、Controller / useWatch / useController がこれを受け取ります。実行時の中身はメソッドの束ですが、TypeScript 上では三つの型引数を抱えた巨大なオブジェクト型です。

2背景（近景） — Control の三つの generic

インストール済み RHF 7.85.0 の型定義は、こうなっています。

export type Control<
  TFieldValues extends FieldValues = FieldValues,
  TContext = any,
  TTransformedValues = TFieldValues
> = {
  _options: UseFormProps<TFieldValues, TContext, TTransformedValues>;
  handleSubmit: UseFormHandleSubmit<TFieldValues, TTransformedValues>;
  register: UseFormRegister<TFieldValues>;
  /* …他の内部フィールド */
};

出典: node_modules/react-hook-form/dist/types/form.d.ts 654 行付近（今日読んだ実ファイル）

三つの席の役割は、公式の TypeScript ページがはっきり書いています。

1. TFieldValues 入力欄・watch・setValue が見る形。デフォルト値やフィールド名はここから決まる。
2. TContext useForm の context オプション。resolver に渡す、フォームの外の情報。未指定なら any。
3. TTransformedValues resolver が検証後に出す形。handleSubmit の成功コールバックがこれを受け取る。省略すると TFieldValues と同じ。

出典: react-hook-form.com/ts 「Many of the types below share two generic parameters… TTransformedValues … defaults to TFieldValues」

第三席がエラーの震源です。resolver の型も同じ三つを持ち、成功時の values に出力型が入ります。

export type Resolver<
  TFieldValues extends FieldValues = FieldValues,
  TContext = any,
  TTransformedValues = TFieldValues
> = (
  values: TFieldValues,
  context: TContext | undefined,
  options: ResolverOptions<TFieldValues>
) => ResolverResult<TFieldValues, TTransformedValues> | Promise<…>;

export type ResolverSuccess<TTransformedValues> = {
  values: TTransformedValues;
  errors: Record<string, never>;
};

出典: node_modules/react-hook-form/dist/types/resolvers.d.ts（今日読んだ実ファイル）

そして UseFormProps は、その resolver を _options.resolver として Control の中にしまっています。赤い波線が _options.resolver の話を始めるのは、ここが原因です。フィールド名でも name の文字列でもなく、箱の中に入っている検証関数の戻り値の型が食い違っている。

export type UseFormProps<…, TTransformedValues = TFieldValues> = Partial<{
  resolver: Resolver<TFieldValues, TContext, TTransformedValues>;
  context: TContext;
  /* … */
}>;

出典: 同 form.d.ts 61 行付近

3直感 — 犬の箱を動物の箱としては渡せない

TypeScript の generic には、三つのはたらき方があります。公式ハンドブックはそれを「分散（variance）」と呼び、こう図示できる関係です。

共変 out T
get: () => T
犬を作る機械は、動物を作る機械として使える
↔
同じ T が
両方に出ると
不変 in out T
get と set の両方
犬の箱 ≠ 動物の箱
↔
受け取るだけ
なら逆向き
反変 in T
set: (v: T) => void
動物を受け取る関数は、犬を受け取る関数として使える

出典: TypeScript Handbook — Variance Annotations（TS 4.7 リリースノートの in / out / in out と同じ説明）

今日、同じ関係を最小の型で測りました。

type Animal = { kind: 'animal' };
type Dog = Animal & { bark: true };

type Box<T> = { get: () => T; set: (value: T) => void };
type Producer<T> = { get: () => T };
type Consumer<T> = { set: (value: T) => void };

declare const dogBox: Box<Dog>;
declare const animalBox: Box<Animal>;

const a: Box<Animal> = dogBox;     // NG  不変
const b: Box<Dog> = animalBox;     // NG  不変
const c: Producer<Animal> = dogBox; // OK  共変
const d: Consumer<Dog> = animalBox; // OK  反変

実測: TypeScript 6.0.3。エラーは variance-toy.ts 11–12 行のみ。13–14 行は無言で通過した

Control は Box に近いです。入力の形を読み書きし（register / _formState）、同時に「検証後の出力」を知る関数（handleSubmit と _options.resolver）も持っている。出力の型 TTransformedValues は、resolver の戻り値にも、handleSubmit が受け取るコールバックの引数にも現れます。出し入れの両方に顔を出す型引数は、構造的に不変に近づきます。

だから次の代入は、犬と動物ほど明らかな親子関係があっても、形が違えば落ちます。

起きていること — 親が持っている箱と、子が欲しがっている箱

親 useForm
Control<入力, unknown, 出力>
入力: { name, billingMethodType } 出力: { name, billing_method_type }
→
props で渡す
子 InputRHF
control: Control<T>
省略された第 3 席は デフォルトで T と同じ ＝ Control<入力, any, 入力>

子は「入力の形だけ知っている箱」を欲しがっています。親が渡そうとしているのは「入力の形と、送信の形の両方を知っている箱」です。TypeScript は、この二つを同じ箱とは認めません。赤い波線は、入力欄の name が間違っていると言っているのではありません。箱の刻印が違うと言っているのです。

よくある誤解

エラーメッセージに discriminated union の展開（{ billingMethodType: "monthly_closing" } | { … "on_demand" }）が長く出るので、「union が複雑だから型が壊れた」と思いがちです。今日の実験では、union を使わないただのオブジェクト { name, billingMethodType } → { name, billing_method_type } でも、同じ _options.resolver エラーが出ました。union はメッセージを読みにくくしているだけで、原理ではありません。

実測ログ: /tmp/2026-08-28-rhf-control-variance-experiment/ を TypeScript 6.0.3 で tsc --noEmit。失敗行の先頭はすべて TS2322 または TS2345

最後の行が教えること

「第 3 席は常に完全一致が要る」は、正確ではありません。TypeScript は Control をラベルで比べるのではなく、中のプロパティを構造的に比べます。resolver の TTransformedValues は戻り値にしか出ないので共変です。出力が入力の部分型なら、その段は通ります。取引先フォームの出力 ClientRequestBody はキー名が違う（billingMethodType 対 billing_method_type）ので部分型ではなく、そこで落ちます。

エラーメッセージを上から読む

今日の失敗ログの典型は、次の階段です。

なぜ useWatch は怒らず、InputRHF は怒るのか

RHF 本体のフックは、すでに第 3 席を開けています。

// useWatch.d.ts — 第 3 席が残っている
control?: Control<TFieldValues, any, TTransformedValues>;

// Controller / useController も同じ
control?: Control<TFieldValues, any, TTransformedValues>;

出典: node_modules/react-hook-form/dist/useWatch.d.ts 26 行、同 types/controller.d.ts の UseControllerProps

今日の実験でも useWatch({ control: controlInUnknownOut, name: 'name' }) は無言で通過しました。同じオブジェクトを (c: Control<T>) => void に渡すと落ちます。

差は実行時の振る舞いではありません。差は受け口の型が第 3 席を覚えているかどうかだけです。Controller に直接渡せば通るものが、その外側を control: Control<T> で包んだ瞬間に落ちる。包んだ人（このリポジトリでは InputRHF）が、RHF が開けておいた席を閉じてしまっている。

公式が書いてある直し方

RHF の PR #11913（「Default TTransformedValues generics to TFieldValues」）は、ラッパーを書く人への移行をこう示しています。第 3 席を追加して、そのまま転送する。

interface ControlledInputProps<
  T extends FieldValues,
  N extends FieldPath<T>,
  U = T,                 // 追加
> {
  control: Control<T, any, U>;  // Control<T> から広げる
}

出典: github.com/react-hook-form/react-hook-form/pull/11913 本文の migration patch。この PR 自体は stale close されたが、同じデフォルト（TTransformedValues = TFieldValues、かつ出力が入力と違う形でもよい）は後続の #11951 / #12638 経由で 7.85.0 の型に入っている

未検証

zumen-fe 全体の pnpm typecheck は、この解説を書くために走らせていません。IDE 上の ClientForm.tsx 214 行の波線が、孤立実験と文字通り同じ階段かどうかは、エディタの診断を開いて突き合わせてください。階段の形（Control<…, ClientRequestBody> が Control<…> に入らず、_options.resolver が先に怒られる）は、型定義と孤立実験から十分に説明できます。

5このコードベースでは

取引先の追加・編集モーダルは、この原理をそのまま踏んでいます。

親は三つ書く

ClientFormProvider は、Zod の discriminated union を入力型にし、送信直前の詰め替えを transform に載せ、RHF に三つ渡しています。

const schema = z.discriminatedUnion('billingMethodType', [
  monthlyClosingTypeSchema,
  onDemandTypeSchema,
]);

export type ClientSchema = z.input<typeof schema>;

const clientFormSubmitSchema = schema.transform(toRequestBody);

export const useClientFormContext = () =>
  useFormContext<ClientSchema, unknown, ClientRequestBody>();

const methods = useForm<ClientSchema, unknown, ClientRequestBody>({
  resolver: zodResolver(clientFormSubmitSchema),
  /* … */
});

出典: src/views/settings/client_settings/components/create_or_edit_modal/ClientFormProvider.tsx 110–145 行。コメントも「各項目は ClientSchema、送信時は ClientRequestBody」と書いている

toRequestBody は camelCase の入力を、API が欲しがる snake_case へ詰め替えます。billingMethodType は billing_method_type になり、Select の { label, value } は value だけになります。入力と出力は部分型の関係にありません。今日の実験の FormIn / FormOut と同じ種類の分裂です。

出典: 同ファイル 154–204 行、および src/types/clientRequestTypes.ts の ClientRequestBody

子は一つしか受け取らない

ClientForm は context から取り出した control を、そのまま共有コンポーネントへ渡します。

const { handleSubmit, control, … } = useClientFormContext();

<ClientFormInputWithLabel
  control={control}
  name="name"
/>

出典: ClientForm.tsx 66–70 行、213–218 行

受け口はこうです。

type Props<T extends FieldValues> = {
  name: Path<T>;
  control: Control<T>;
  /* … */
};

出典: src/views/settings/client_settings/shared/ClientFormInputWithLabel.tsx 9–12 行。同じ形は ClientFormTextareaWithLabel.tsx、src/components/forms/input/InputRHF.tsx 21 行、CheckboxGroupRHF.tsx 17 行、SelectRHF.tsx 35 行

src/components/forms 配下を grep すると、control: Control<T> は 15 ファイルにあります。どれも第 3 席を閉じています。ほとんどの画面は useForm<Schema> か useFormContext<Schema> の一つだけなので、第 3 席のデフォルトが Schema のまま残り、波線は出ません。

三つ書く useForm は、少なくとも次の場所にあります。

ファイル第 1 席第 3 席
ClientFormProvider.tsx ClientSchema ClientRequestBody
OrderSearchFormProvider.tsx OrderSearchFormSchemaInput OrderSearchFormSchema
OrderKanbanSettingFormProvider.tsx z.input<typeof schema> OrderKanbanSettingFormSchema
UpdateOrderStatusFormProvider.tsx UpdateStatusFormSchema UpdateStatusFormSubmitSchema

grep: useForm< の複数行。案件検索側には「入力と出力を揃えれば useForm<Schema> に戻せる」という TODO がある（src/zod_schema/orderSearchFormSchema.ts 45–50 行）

同じリポジトリの中で、二つの流派が同居しています。一つは「resolver で形を変えるなら三つ書け」（公式の推奨、取引先モーダル）。もう一つは「入力と出力を同じ型に揃えて、第三者を消す」（案件検索の TODO）。赤い波線は、前者を選んだ親が、後者の前提で書かれた子に control を渡したときにだけ現れます。

直し方の地図（実装はしていない）

原理から見える道は三つです。①共有コンポーネントの受け口を Control<T, any, TOut> に広げて第 3 席を転送する（PR #11913 の公式移行）。②resolver では形を変えず、送信ハンドラで toRequestBody する（第 3 席がデフォルトのまま残り、Control<T> と一致する）。③親の context を入力型だけに戻し、送信時だけ別関数で出力型を付ける（ClientForm.tsx 71 行にコメントアウトされた useClientFormHandleSubmit は、この方向を一度試した跡に見える）。

未検証

BillingTransactionForm は同じ FormProvider の下で useFormContext<BillingTransactionFormValues>() と、より狭い型を名乗っています（BillingTransactionForm.tsx 34 行）。これが今 IDE で波線になっているかは測っていません。原理的には第 1 席の不変性（実験 C）の話で、第 3 席の話とは別件です。
