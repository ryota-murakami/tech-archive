1. 背景

1.1 基礎から（知っている人は 1.2 へ）

HTTP は記憶を持ちません。サーバーにとって、あなたの二回目のリクエストは見知らぬ誰かの一回目と区別がつきません。だから「さっきログインした本人です」という証拠を、リクエストのたびに添える必要があります。認証まわりの用語はほぼすべて、次の二つの問いへの答え方の違いです。

問い一：証拠をどう運ぶか

  • Cookie：サーバーが一度預けると、ブラウザが条件に合うリクエストへ自動で添付します。人間が使う Web アプリ向きです。
  • Authorization ヘッダー：プログラムが明示的に添付します（Authorization: Bearer …）。サーバー同士の API 呼び出し向きです。

問い二：証拠の中身は何か

  • 参照型：ただのランダムな番号です。サーバーが台帳を引いて「この番号は誰のものか」を調べます。台帳から消せば即座に無効になります。
  • 自己完結型（JWT）：「私は誰で、いつまで有効か」を書いた申告書に、発行者が署名したものです。受け取った側は署名を確かめるだけでよく、台帳を引きません。速い代わりに、期限が来るまで取り消しにくくなります。
認証と認可は別の問い 認証（authentication）は「あなたは誰か」。認可（authorization）は「何をしてよいか」。OAuth 2.0 は認可の仕組みで、OIDC がその上に認証を足します。この区別が 3.2 と 3.3 の軸になります。

1.2 今回の問いに直接関わる背景

GitBox で「GitHub でログイン」を一回押すと、三種類の証拠がまとめて動きます。ボタンは一つなのに登場人物は四者（ブラウザ、GitBox の Next.js サーバー、Supabase Auth、GitHub）で、ここが混乱のもとです。先の質問に対する短い答えは次のとおりです。

  • user_session は github.com 自身のログイン Cookie で、GitBox とも Supabase とも関係がありません。文書 GitHub は「This cookie is used to log you in.」と説明しています。
  • GitBox のログイン状態を持っているのは Supabase です。Next.js のサーバーは何も覚えておらず、毎回 Cookie から読み直して検証しています。コード

2. 直感：三枚の証明書

会社のビルに例えます。あなたは三枚の紙を持ち歩いています。

  1. GitHub の会員証（user_session）。GitHub 本店の受付で見せるもので、GitHub が発行し、GitHub だけが読めます。

3. 仕組み

三枚の紙を運んでいるのは Cookie で、③を発行する手続きが OAuth 2.0、②の中身の形式が JWT（OIDC で広まった形式）です。下から順に積み上げます。

3.1 Cookie の特性

Cookie は、サーバーが Set-Cookie ヘッダーで預け、ブラウザが条件に合うリクエストへ自動で添付する小さな文字列です。「自動で添付される」ことが便利さの源であり、危険の源でもあります。文書 RFC 6265 はこれを ambient authority（その場にあるだけで効く権限）と呼び、CSRF の原因だと述べています（§8.2）。属性はすべて、いつ添付するか・誰が読めるかを絞るためのものです。

属性何を絞るか要点 文書（MDN）
HttpOnly誰が読めるかJavaScript（document.cookie）から読めなくなる。リクエストには付く。
Secureどの通信に付くかhttps: のときだけ送る。localhost は例外。
SameSiteどこ発のリクエストに付くかStrict：同一サイト発のみ。Lax：それに加えて、クロスサイトでも「トップレベルの画面遷移」かつ安全なメソッド（GET）なら付く。None：常に付く（Secure 必須）。
Domainどのホストに付くか省略するとセットしたホスト限定（host-only）。指定するとサブドメインにも付く。
Pathどのパスに付くかセキュリティ目的の仕組みではない、と明記されている。
Max-Age / Expiresいつまで残るかどちらも無ければ「セッション Cookie」。ブラウザを閉じると消える（復元機能で残ることもある）。
__Host- 接頭辞名前による自己申告Secure 必須、Domain 禁止、Path=/ 必須。条件を破るとブラウザが受け取らない。

実際に測る

文章だけでは Lax の境界がつかみにくいので、二つのホストを立てて測りました。サイト A（http://localhost:4801）で 8 個の Cookie をセットし、いろいろな種類のリクエストにどの Cookie が付いて届いたかをサーバー側で記録しています。サイト B は http://127.0.0.1:4802 で、A から見て別サイトです。下のボタンで切り替えてください。

実測 HeadlessChrome 154、2026-10-11。緑＝サーバーに届いた、薄い＝届かなかった、点線＝そもそもブラウザが保存を拒否した。

この計測から、あとで効いてくる事実が六つ取り出せます。

  1. ブラウザは条件を満たさない Cookie を黙って捨てる。 SameSite=None なのに Secure が無いもの、__Host- なのに Domain を付けたものは保存されませんでした。エラーは出ません。
  2. HttpOnly は「読めない」であって「送られない」ではない。 document.cookie に honly は現れませんが、fetch には付いて届きました。XSS でトークンを盗み出すことは防げますが、XSS がそのページからリクエストを送ることは防げません。
  3. Cookie はポートを区別しない。 localhost:4801 でセットした 6 個すべてが localhost:4802 に届きました。文書 RFC 6265 §8.5「Cookies do not provide isolation by port.」
  4. 別サイトからの fetch には SameSite=None しか付かない。 他人のサイトがこっそりあなたの権限で API を叩く攻撃（CSRF）への、ブラウザ側の既定の防御です。
  5. 別サイトからのリンク遷移（トップレベルの GET）には Strict 以外すべて付く。 ここが OAuth を成立させる要です。GitHub から GitBox へ戻ってくるリダイレクトはまさにこの種類のリクエストで、Lax の Cookie（PKCE の合言葉を入れたもの）が付いて届くからログインが完了します。Strict にしていたら届きません。
  6. 「属性なし」は Lax と同じではない。 セット直後の 2 分間だけ、SameSite 無指定の Cookie は別サイトからの POST にも付きました。130 秒後には付かなくなりました。明示的に SameSite=Lax と書いた Cookie は、直後でも付きませんでした。文書 MDN も「set no more than two minutes before」と書いています。
「サイト」と「オリジン」は違う オリジンはスキーム＋ホスト＋ポートの組です。サイトはもっと粗く、ざっくり言えば「登録できるドメイン」の単位です。SameSite が見るのはサイトで、Cookie の保管単位はホストです。だから localhost:3008（GitBox）と localhost:54321（ローカル Supabase）は別オリジンですが同一サイトで、Cookie 入れも共有します。

大きさと寿命

  • 文書 ブラウザは Cookie 1 個あたり少なくとも 4096 バイトを扱えるべき、と RFC 6265 §6.1 が定めています。保証されているのはここまでなので、これを超える値は 1 個の Cookie には入らないものとして設計します。
  • コード実測 Supabase のセッションは 1 個に収まらないので、@supabase/ssr 0.12.7 は 3180 文字ごとに分割します（MAX_CHUNK_SIZE = 3180）。本番の Cookie を測ると、…auth-token.0 がちょうど 3180 文字、.1 が残りの 781 文字でした。
  • コード実測 同ライブラリの既定の maxAge は 400 日で、計測した Cookie の残り寿命も最大 400 日でした。ソースのコメントは Chrome の上限を理由に挙げています。未確認 Chrome の上限そのものは今回測っていません（401 日を指定した Cookie の expires を読めば確かめられます）。

3.2 OAuth 2.0：権限を委ねる手続き

Cookie が運び屋だとすると、OAuth 2.0 は「委任状」を安全に発行する窓口の手順書です。文書 RFC 6749 の言葉では、第三者のアプリが HTTP サービスへの「limited access」を得るための枠組みです。合言葉はパスワードを渡さずに、権限の一部だけを渡す。

RFC 6749 の役割定義 文書GitBox では
Resource owner保護された資源へのアクセスを許可できる存在あなた
Clientresource owner の許可を得て、代わりに資源へリクエストするアプリGitHub に登録した OAuth App「GitBox Tokyo」。秘密鍵を持って実際に GitHub と話すのは Supabase Auth
Authorization server本人を確かめ、許可を得て、access token を発行するサーバーgithub.com/login/oauth/…
Resource server資源を持ち、access token つきのリクエストに応えるサーバーapi.github.com

なぜ「コード」を一度はさむのか

Authorization Code Grant は、ブラウザを経由する表の道と、サーバー同士の裏の道を使い分けます。ブラウザの URL に載るのは 10 分で失効する引換券（code）だけで、本物のトークンは裏の道でしか流れません。文書 GitHub の code は「will expire after 10 minutes」です。

二つの安全装置：state と PKCE

  • state：行きに付けた推測不能な値が、帰りにも同じ値で付いているかを確かめます。文書 GitHub の説明では CSRF 対策で、一致しなければ「you should abort the process」。攻撃者が自分の code を被害者のブラウザに踏ませて、被害者を攻撃者のアカウントにログインさせる攻撃を防ぎます。
  • PKCE（ピクシー、RFC 7636）：引換券の横取りへの対策です。クライアントは最初にランダムな合言葉 code_verifier を作って手元に置き、そのハッシュだけを先に送ります。引換のときに合言葉そのものを出し、サーバーが照合します。
code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))   // RFC 7636 §4.2

行き:   code_challenge を送る（ハッシュなので見られても困らない）
帰り:   code を受け取る
引換:   code と code_verifier を送る
検証:   サーバーが同じ式で計算し、行きの code_challenge と一致するか確かめる

実測 supabase-js に実際に認可 URL を作らせると、code_challenge は 43 文字（32 バイトの SHA-256 を base64url にした長さ）、code_challenge_method は s256 でした。合言葉は sb-<ref>-auth-token-flow-<id>-code-verifier という名前で保存されます。サーバー側のフローでは保存先が Cookie なので、3.1 の「リンク遷移には Lax が付く」がここで効きます。

GitHub の OAuth App に固有の事実 文書

  • トークン交換には client_secret が必須です。秘密を持てるサーバー側クライアント（confidential client）が前提です。
  • 応答は access_token=gho_…&scope=…&token_type=bearer。id_token はありません（3.3 で効いてきます）。
  • スコープ repo は「full access to public and private repositories including read and write access to code」。GitBox が要求しているのはこれです。ただし「They do not grant any additional permission beyond that which the user already has」。
  • OAuth App のトークンに有効期限の記載はありません。失効するのは、1 年間使われなかったとき、同じユーザー・アプリ・スコープの組で 10 個を超えたとき（古いものから）、ユーザーまたはアプリ所有者が取り消したとき、公開リポジトリに push されたときです。
  • 比較：GitHub App のユーザートークンは既定で 8 時間で切れ、refresh token で更新します。OAuth App とは別物です。
よくある誤解：「OAuth でログインする」 OAuth 2.0 が発行するのは委任状であって、身分証ではありません。access token は「この持ち主は GitHub でこれをしてよい」としか言っておらず、RFC 6749 も「usually opaque to the client」と書いています。クライアントは中身を読めないのです。それでも「GitHub でログイン」が成り立つのは、受け取った委任状で GET /user を呼び、返ってきた答えを本人情報として扱っているからです。この「委任状で本人情報を聞きに行く」部分を標準化したものが、次の OIDC です。

3.3 OIDC と JWT：「誰か」を証明する層

文書 OpenID Connect は自分を「a simple identity layer on top of the OAuth 2.0 protocol」と定義しています。OAuth の手順はそのままに、三つを足します。

  1. リクエストに openid スコープを入れる（「MUST contain the openid scope value」）。
  2. トークン応答に ID Token が加わる。これは「誰が、いつ、どこで認証されたか」を書いた JWT です。
  3. 追加の本人情報を返す UserInfo エンドポイント。
ID Token の必須クレーム意味 文書クライアントが確かめること
iss発行者期待する発行者と完全一致するか
sub発行者の中で一意で、再割り当てされない利用者 ID—（これがユーザーの主キーになる）
aud宛先。クライアントの client_id を含まなければならない自分宛てか。違えば拒否
exp / iat失効時刻 / 発行時刻現在時刻が exp より前か
nonceリクエストと ID Token を結びつける値自分が送った値と同じか（再送攻撃対策）

実測 全体で 942 文字、exp − iat は 3600 秒でした。公開鍵は /auth/v1/.well-known/jwks.json にあり、同じ kid の ES256（P-256）鍵が載っていました。受け取った側はこの公開鍵で署名を確かめるだけでよく、Supabase に問い合わせる必要がありません。これが「自己完結型」の意味です。

JWT は封筒ではなく、署名入りのはがき 署名が保証するのは「書き換えられていない」ことだけで、「読まれない」ことではありません。JWT に秘密を入れてはいけませんし、JWT そのものが盗まれれば期限までそのまま使えます。

GitHub ログインは OIDC ではない

ここまで来ると、GitBox のログインの位置づけがはっきりします。

  • 文書コード GitHub の OAuth App の応答に ID Token はなく、Supabase Auth の GitHub プロバイダーも openid スコープや ID Token を扱いません。代わりに、受け取った access token で api.github.com/user と /user/emails を呼んで本人情報を得ます（ソース internal/api/provider/github.go）。
  • 実測 その痕跡はスコープに出ます。GitBox が頼んだのは read:user user:email repo ですが、Supabase が GitHub に送った URL のスコープは user:email read:user user:email repo でした。先頭の user:email は Supabase が自分のために足したものです。
  • つまり流れは「OAuth 2.0 ＋ API 呼び出し」です。一方、Supabase が GitBox に渡す入館証②は JWT で、形式としては ID Token の親戚です。GitHub との間は OAuth、Supabase との間は JWT、と覚えておくと混ざりません。

OIDC は人間だけのものではない

OIDC の ID Token は「この実行環境は誰か」の証明にも使われます。文書 Vercel は関数のリクエストに x-vercel-oidc-token ヘッダーで JWT を渡します。iss は https://oidc.vercel.com/[TEAM_SLUG]、sub は owner:[TEAM_SLUG]:project:[PROJECT_NAME]:environment:[ENVIRONMENT] です。AWS などがこの発行者を信頼するよう設定しておくと、長期の秘密鍵を置かずにクラウドの権限を借りられます。

入館証②の一生

②は「短命な JWT」と「長命な refresh token」の二人組です。JWT が切れそうになると、refresh token を新しい二人組と交換します。文書 refresh token は「never expire but can only be used once」。使用済みのものがもう一度使われたら、盗まれたと見なしてセッション全体を終了させます（同時リクエストのための猶予は既定 10 秒。コード ローカルの config.toml も refresh_token_reuse_interval = 10）。

有効

更新

終了
サインアウトでセッション行が削除され、refresh token は使えなくなる
未確認：サインアウト後、発行済みの JWT はいつまで通るか Supabase の文書は明言していませんが、強く示唆しています。サインアウトを検知したければ「session_id クレームが auth.sessions の行に対応するか確認できる」とあり、それは「最も機微な操作にだけ」使うよう勧めています。裏を返せば、署名だけを見ている限り JWT は exp（最長 1 時間）まで通るはずです。確かめるには、ローカルでログイン → access token を控える → サインアウト → その token で保護されたページを叩く、で分かります。

手で切る場所

どこで切るか切ると何が起きるか
① 会員証github.com/settings/sessions で該当セッションを Revoke。またはそのブラウザで GitHub からサインアウトそのブラウザの github.com がログアウト状態になる。②③は別の紙なので影響しない（仕組みからの帰結。計測はしていません）

ローカル開発で起きること

実測 http://localhost:3008 宛ての Cookie を数えると 21 個あり、GitBox のものは一部でした。残りは同じマシンで動かした別のアプリ（Auth.js 系、Clerk 系など）のものです。3.1 の事実 3 のとおり、localhost の Cookie 入れは全ポート共有なので、GitBox の開発サーバーには他のアプリのセッション Cookie も届いています。逆も同じです。害が出る場面は限られますが、「ローカルで妙にヘッダーが大きい」「別アプリのログインが混ざる」ときの原因になります。アプリごとに 127.0.0.1 と localhost を使い分けるか、*.localhost のサブドメインを使うと分かれます。
