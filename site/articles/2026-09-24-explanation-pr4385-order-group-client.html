1. 先に結論 (30 秒で)

  • 案件グループは、関係する複数の案件を 1 つの束にまとめる仕組みです。1 グループ = 1 顧客というルールがあります。
  • 「新規案件を作成」モーダルの案件グループ名の欄には、既存のグループを選ぶか、新しい名前を入力して新規作成するかの 2 通りがあります。
  • 修正前は、顧客名を選ぶたびにこの欄が無条件で空に戻っていました。既存グループなら理にかなった処理です (別の顧客のグループかもしれないので)。ですが、入力した新しい名前はまだどの顧客のものでもないので、消す必要がありませんでした。
  • 修正後は、新しい名前は残し、既存グループは「選んだ時点の顧客」と違う顧客になったときだけ外します。

以下では、この 4 行を 1 行ずつ説明していきます。「案件グループ」がそもそも何なのかから始めます。

2. 背景 — 案件・顧客・案件グループ

2-1. 入門: 3 つの登場人物 (ズメーンのデータモデルを知っている方は読み飛ばして構いません)

ズメーンは、製造業の見積・受注の仕事を図面を中心に管理するアプリです。この PR に出てくる言葉は 3 つだけです。

📐 案件 (order) 1 件の引き合い・受注の単位です。図面ファイルを持ち、ステータス (見積中、製作中…) を持ち、顧客を持ちます。案件一覧 (/orders/table と /orders/kanban) に並ぶ 1 行 / 1 枚のカードが 1 つの案件です。
🏢 顧客 (client) 案件の依頼主です。案件の「顧客名」欄で選びます。未設定 (null) でも構いません。
📦 案件グループ (order group) 関係する複数の案件をまとめる束です (#4212 で入った新しい機能)。要件定義「案件グルーピング」の決まりは次のとおりです。
  • すべての案件は、必ずどれか 1 つのグループに属します (未分類は無い)。グループを指定せずに案件を作ると、BE がその案件のためだけの新しいグループを作ります。
  • グループには自動で振られる番号と、任意の名前があります。名前を使うかどうかは会社ごとの設定です。
  • 原則 1 グループ = 1 顧客。ただし顧客が null の案件は、どのグループに混ざってもよい。

1 グループ = 1 顧客を図にすると次のようになります。

📦 グループ #9「A社 フランジ一式」
顧客: A社
・案件 101 (顧客 A社)
・案件 102 (顧客 A社)
・案件 103 (顧客 null) ← 混ざってよい
📦 グループ #10「B社 試作」
顧客: B社
・案件 104 (顧客 B社)
✕ 顧客 A社 の案件は入れられない

案件一覧では、「ステータスごとの設定 > 表示設定」で「案件グループでまとめて表示」にしたステータスの案件が、グループ単位でまとめて並びます。

2-3. 保存すると BE で何が起きるか

「案件を作成」を押すと、フォーム値は convertOrderGroupSelectionToRequest で API の形に変換され、BE に送られます。

FE フォーム値
order_group: { name: "12345" } client_name: A社 (id 5)
→
POST /api/drawing_files
order_group: { name: "12345" } client_id: 5
→
BE
① 顧客 null の新しいグループ「12345」を作る
② 案件 (顧客 A社) をそこへ入れる
③ グループの顧客を案件の顧客 (A社) で埋める
FE フォーム値
order_group: { id: 9, number: "…" } client_name: B社 (id 7)
→
POST /api/drawing_files
order_group: { id: 9 } client_id: 7
→
BE
グループ #9 の顧客は A社、案件の顧客は B社
→ 両方に顧客があって食い違うので 422 client_conflict
「案件グループには 1 つの顧客しか設定できないため…」
🔑 BE から見た非対称性
  • 新しい名前 { name }: まだ誰のものでもありません。顧客が何であっても、保存時にその案件の顧客のグループになります。顧客が変わっても壊れようがありません。
  • 既存グループ { id }: すでに特定の顧客のものです。違う顧客の案件を入れようとすると 422 で弾かれます。
この PR の直し方は、ほぼこの非対称性から導けます。

原因は、顧客名セレクトに付いていた、この 1 行です (#4212 で入ったもの)。

// NewOrderDrawingBasicItemsForm.tsx (修正前)
onChange={() => setValue('data.order_group', null)}
onCreationSuccess={(newClient) => {
  setValue('data.drawing_basic_items.client_name', { label: newClient.name, value: newClient.id });
  // 1 グループ = 1 顧客のため、顧客が変わったらグループ選択は捨てる
  setValue('data.order_group', null);
}}

コメントにあるとおり、狙いは「1 グループ = 1 顧客」を守ることでした。A社のグループ #9 を選んだあとで顧客を B社に変えたら、#9 を残しておくと保存時に 422 になります。だから外す。これ自体は正しい考えです。

問題は、外す相手を区別していなかったことです。前の節で見たとおり、新しい名前 { name } はまだどの顧客のものでもないので、顧客が変わっても守るべきルールに触れません。それを既存グループと同じように捨てていました。そしてモーダルの並び順のせいで、上から入力するユーザーは毎回この罠を踏みます。

🐛 一言でいうと 「既存グループを守るための処理」が、「新しいグループ名」まで巻き込んで消していた。

onChange で顧客の変更前後の値を比較し、実際に顧客が変わった場合だけグループをリセットする。

一見もっともらしいのですが、報告の手順に当てはめてみると直りません。

具体例で並べると、修正前と修正後の違いは 3 行に集約されます。

案件グループ名の欄顧客名の操作修正前修正後
新しい名前 12345選ぶ / 別の顧客に変える / × で消す / 顧客を新規作成空になる残る

既存グループ #9 (A社で選択)B社に変える / × で消す / 顧客を新規作成空になる空になる (変更なし)
🤔 「既存グループ → 顧客を × で消す」はなぜ外すのか BE の決まりでは、顧客 null の案件はどのグループにも入れるので、残しても 422 にはなりません。それでも外すのは、この欄が「顧客が未選択なら既存グループは選べない」作りだからです。顧客を消したのに既存グループだけが残っていると、ユーザーが自分では作れない状態が画面に出てしまいます。修正前もこの場合は外していたので、挙動は変わりません。
📝 残した新しい名前は、既存グループと突き合わせません 「12345」を入れてから、たまたま「12345」という既存グループを持つ顧客を選んでも、保存時には新規作成になります (BE はグループ名の重複を禁止していません)。顧客を先に選んでから「12345」を新規作成した場合と同じ結果なので、今回は変えていません。

3-4. 「選んだ時点の顧客」を覚えさせる

残る問いは、「既存グループを選んだ時点の顧客」をどこから持ってくるかです。素直に考えると「顧客名の onChange の中で、変更前の顧客をフォームから読めばいい」となりますが、そうはいきません。顧客名セレクトの土台 CreatableSingleSelectRHF は、呼ぶ順番が決まっているからです。

  1. ユーザーが顧客名で「B社」をクリックする
  2. field.onChange(B社) — react-hook-form のフォーム値が B社に書き換わる
  3. 呼び出し側の onChange が呼ばれる — ここで getValues('…client_name') を読んでも、返ってくるのはもう B社。変更前の A社はどこにも残っていない
// CreatableSingleSelectRHF.tsx L81-82
onChange={(e, meta) => {
  field.onChange(e, meta);          // ① 先にフォーム値を更新
  if (onChange) onChange(e, meta);  // ② そのあと呼び出し側へ
}}

最初の実装は、useWatch で購読している「直前の描画時点の顧客」を変更前の値として使っていました。動きはしますが、「描画のタイミングの都合でたまたま古い値が見えている」ことに正しさが依存していて、コードを読んでもそれで正しい理由が分かりません。セルフレビューでこの点を指摘され、次の形に作り直しました。

✅ 採用した形: 選択値そのものに持ち主を書いておく 既存グループを選んだ瞬間に、その選択値に client_id (そのとき選ばれていた顧客) を書き込んでおきます。候補は選択中の顧客で絞り込んで取っているので、候補から選んだグループの持ち主は、その時点の顧客と必ず一致します。
こうしておけば、あとで顧客が変わったときは「選択値の client_id」と「変更後の顧客」を比べるだけで判定できます。変更前の顧客も描画のタイミングも要りません。
① 顧客 A社 (id 1) で既存グループ #9 を選ぶ
order_group: { id: 9, number: "20260825-9", client_id: 1 ← 追加 }
→
② 顧客を B社 (id 2) に変える
判定: client_id 1 !== 2
→ 外す (null)
→
(もし A社のまま保存したら)
order_group: { id: 9 }
client_id は送らない

client_id は FE の中だけで使う目印で、API には出ません。送信データは今までどおり convertOrderGroupSelectionToRequest が { id } か { name } だけに絞ります。BE から見ると、この PR の前後で何も変わりません。

4. コード — 変更を順に読む

プロダクトコードの変更は 5 ファイル、+113 −25 行です。PR 本文のおすすめどおり、判定の中心から外側へ読んでいきます。

4-1. 判定の純関数 checkShouldClearOrderGroupOnClientChange (新規)

3-3 の分かれ道を、そのままコードにしたものです。React にも react-hook-form にも依存しないので、単体で 7 件のテストがあります。

// src/functions/checkShouldClearOrderGroupOnClientChange.ts
export const checkShouldClearOrderGroupOnClientChange = ({
  orderGroup,
  nextClientId,
}: {
  orderGroup: OrderGroupSelection;
  nextClientId: Client['id'] | undefined;
}): boolean => {
  // 未選択、または入力した名前で新規作成するグループ (id を持たない) は、どの顧客にも属していない
  if (orderGroup == null || !('id' in orderGroup)) return false;

  // 選んだ時の顧客が分からない既存グループは、別の顧客のものかもしれないので外す
  if (orderGroup.client_id == null) return true;

  return orderGroup.client_id !== nextClientId;
};

3 行の if / return が、分かれ道の 3 本の枝にそのまま対応しています。nextClientId が undefined (顧客を × で消した) なら、最後の比較は必ず「違う」になるので、既存グループは外れます。

    number: z.string(),
    name: z.string().optional(),
+   // このグループの顧客。選択肢は選択中の顧客で絞り込んで取得するので、選んだ時点の顧客を入れる
+   client_id: z.number().optional(),
  }),
  // 入力した名前で新規作成
  z.object({ name: z.string().min(1).max(ORDER_GROUP_NAME_MAX_LENGTH) }),
]).nullable();
💡 なぜ必須ではなく optional なのか この union には「どちらの形か」を示す判別キーがありません。もし client_id を必須にすると、client_id が欠けた既存グループの値 ({ id, number, name }) は 1 つ目の形に合わなくなります。すると zod は 2 つ目を試し、name があるので「新しい名前の新規作成」として通してしまいます。既存グループのつもりが新規作成に化けるより、optional にして「client_id が無い既存グループは外す」(4-1 の 2 本目の if) で安全側に倒す方を選んでいます。

4-5. 変わっていないもの

  • API と BE: 送信データは { id } か { name } のまま。client_id が送信データに出ないことを convertOrderGroupSelectionToRequest.spec.ts で固定しています。
  • 欄の並び順: 案件グループ名が顧客名より上のまま。要件定義に「左カラムの一番上(モーダル内の最初の入力フォーム)に配置する」とあるためです。チケットの補足にあった並び順の見直しは仕様変更なので、PdM の判断事項として残っています。
  • 案件グループの移動モーダル: 別のピッカー (OrderGroupPickerModal) を使っているので影響しません。
